# External reviewer and owner checklist

This packet is ready for criticism, not proof that independent review occurred.
Do not use the physical Pi to reproduce it.

1. Verify the candidate commit, archive checksum and inner inventory. Confirm
   notices are present and no guest disks, credentials, transcripts, models or
   executables are included. Compare two locally produced source archives.
2. Follow [the clean-checkout demonstration](../getting-started/source-alpha.md)
   without private workspace state. Check simulation labels, offline reference
   tools, shutdown and removal. Record your exact host/browser versions.
3. Run the [security packet's named tests](../security/M5.13-review.md). Inspect
   authority transitions and boundaries, especially process versus guest identity,
   consent after revocation, filesystem ownership and resource exhaustion.
4. Review [the independent-app interface](../technical/hacker-replicant-interoperability.md)
   against the pinned upstream source. Do not contact the upstream maintainer or
   treat the preparation patch as accepted upstream work.
5. With your own authorized media, reproduce the V7 lab and inspect the RT-11
   generation/status findings. Keep console, serial, browser, application and
   full-diagnostic results separate. RSTS remains blocked on generation materials.
6. Review actual tutor answers and held-out cases. Check quoted wording against
   real primary passages; an ID match is not quotation validity. Look for false
   certification and limitations hidden by a correct core answer.
7. Decide whether to publish **source only**, scoped to demonstration and controlled
   labs. Keep physical deployment, general service installation, stable release
   and public binary downloads outside that decision.

## Future physical acceptance — not executed in M5.13

A separately authorized supervised plan must establish all of the following:

| Gate | Required observable result / stop condition |
| --- | --- |
| Repaired SR0 and neighboring momentary switch | Owner verifies mechanical function; original scanner measures stable deassert/assert/deassert and correct neighboring behavior. Stop on stuck/intermittent bits. |
| Original scanner and exclusive GPIO | Known original binaries/source; only one scanner/panel owner; measured bounded samples match owner-confirmed positions. No Web Desktop dependency. |
| Original REALCONS/panel | Owner observes real lamps, HALT and CONT, selectors and momentary controls with the original installation. Software state is not substituted for a lamp observation. |
| Original boot selection | Physical selection and no-argument launcher boot the expected original profiles; explicit selection argument behavior remains distinguished. Stop at any wrong guest. |
| Kernel memory readiness | Actual running kernel exposes effective cgroup memory/swap controllers; 96 MiB hard limit and zero swap enforced before service listens. No bypass of the refusal guard. |
| Companion installation | Reviewed package/configuration, stopped and disabled by default; original files/media hashes unchanged; no automatic emulator start/stop or GPIO access. |
| Guest-line approval | Independently verify current guest and dedicated line; fresh instance/revision approval; new browser read-only; observer cannot type. Stop actual bridge before guest change. |
| Independent recovery access | Screen, SSH and supported serial routes work before, during and after companion failure/removal. Browser is never the only console. |
| Failure and rollback | Service crash/restart leaves new instance detached; original guest survives; rollback restores matching prior configuration while stopped; removal restores original stopped/running state as explicitly agreed. |
| Pi 3B+ sustained resources | At least 30 minutes of representative terminal/observer/peripheral work; report RSS/heap, CPU, latency distribution, descriptors, kernel memory events, temperature and throttling with emulator-only baseline. No OOM, unbounded growth or unexplained guest/panel impact. |

Retained targets remain bridge RSS below 32 MiB in ordinary operation, hard service
ceiling 96 MiB with zero swap, idle CPU below 1% and active average below 5% of one
Pi core, browser rendering local to the client. Report command latency including
SIMH polling separately from bridge overhead; aim for under 100 ms bridge delivery
and under 1 s end-to-end interactive response in the defined workload. A Mac
measurement does not satisfy these Pi gates, and failures must not be relabeled as
passes by changing the workload or removing containment.
