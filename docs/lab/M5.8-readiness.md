# M5.8 readiness: a staged, optional installation

**Preparation during M5.7, updated by M5.7.1, November 19, 2026. This is a proposed procedure, not deployment authorization or a record of installation.** Physical sampling and its interpretation belong in the M5.7 diagnostic report. No stable scanner result alone proves that the M5.5 intermittent selection discrepancy cannot recur.

The M5.6 foundation already implements detached startup, explicit local attachment, generation-bound browser connections, private credentials, service isolation and reversible packaging. M5.7.1 adds tested kernel-memory verification and refusal before listeners open. The first installed stage should prove that the desktop is optional **with the emulator stopped**. Guest/physical coexistence follows only under a separately reviewed supervised guest plan.

**Readiness blocker:** the actual Pi reports `cpuset cpu io pids` in `/sys/fs/cgroup/cgroup.controllers`, without `memory`, and `/proc/cmdline` explicitly contains `cgroup_disable=memory`. This confirms a boot-time disabling setting, not a missing companion package. Do not infer that `MemoryMax=96M` is enforceable merely because systemd accepts the unit text. Memory accounting/limits need separate resolution and authorized validation. M5.7.1 now refuses protected companion startup under missing local enforcement; its Linux lab demonstrated that systemd can report the configured limit even when the required kernel files are absent. This refusal does not resolve the Pi prerequisite. No boot settings, kernel configuration or service settings were changed to address this finding.

No package, account or service has been installed by this readiness work. The observed absence of companion paths is a preflight fact, not proof of a future uninstall.

## Stage 0: review and baseline — no service start

1. Obtain explicit M5.8 authorization identifying whether it covers detached-only installation, a supervised copied-media guest pilot, or both. Confirm owner availability for physical checkpoints. Keep M5.7 diagnosis and M5.8 guest operation separate.
2. Record current original operation and intended fallback. If selection remains uncertain, do not boot an original writable guest to test the installer. A detached-only installation can be considered separately; it cannot earn physical-coexistence acceptance.
3. Select an immutable version label and verify the complete package with `PACKAGE_SHA256SUMS`. Record source commit, executable digest, architecture and private configuration backup destination. Refuse existing unmanaged paths or account conflicts; do not overwrite a release.
4. Check free space, available memory, temperature/throttling, current processes/listeners, original file metadata and the expected stopped state. Choose which original-media checks are explicitly authorized; M5.7 itself does not open guest disks.

Use the [existing owner setup procedure](../getting-started/optional-service.md) for exact Linux commands. The tested M5.7.1 candidate and validation scope are recorded in [M5.7.1](M5.7.1.md). Preserve the earlier M5.6 package; a new build requires its own digest and relevant tests.

## Stage 1: install, configure and open the detached desktop

1. Install the companion only. Verify its dedicated non-login account has no GPIO, disk, emulator or administrator membership. Verify the unit is stopped and disabled. Original processes and files must remain as recorded.
2. Run first-time configuration for the reviewed bind address, exact HTTPS origin and reserved loopback guest endpoint. No guest connection is needed. Run `webdesktop-service check` under the dedicated account; confirm certificate expiry/name, private permissions and detached startup policy. Do not print token contents into the report.
3. Review the **effective** unit with `systemctl cat` and `systemctl show`, not only its packaged text. Confirm `Restart=no`, `User`/`Group`, private runtime directory, empty capabilities, `NoNewPrivileges=yes`, `PrivateDevices=yes`, `ProtectSystem=strict`, `ProtectHome=yes`, protected kernel/control-group settings, `InaccessiblePaths=-/opt/pidp11`, `MemoryMax=96M`, `MemorySwapMax=0`, `Environment=GOMEMLIMIT=72MiB`, `ExecStart` including `-require-memory-limit`, and `TasksMax=64`. There must be no dependency pulling in the original launcher, emulator or panel daemon.
4. Start only `pidp11-webdesktop.service`. Verify its actual cgroup `memory.max` is 100663296 and `memory.swap.max` is 0; a startup refusal leaves this checkpoint failed. Verify a new instance with every endpoint detached and no new guest connection. Record the actual process, control group and sole intended HTTPS listener. Do not enable autostart.
5. Open the desktop from the approved browser route. Confirm simulated panel/peripherals are labeled; both writer and observer sign-in work; incorrect credentials fail; no-guest state leaves Connect disabled. Refresh must not start or attach anything. Closing/reopening the page must not acquire a keyboard.
6. Stop and restart only the companion. Previous cookies, attachment approvals and keyboard leases must not survive. Verify the original emulator is still stopped. This is the end of detached-only acceptance.

The [systemd 257 execution manual](https://www.freedesktop.org/software/systemd/man/257/systemd.exec.html) describes these filesystem/device restrictions. They still require actual kernel validation. `PrivateNetwork` is deliberately absent so approved loopback guest lines remain reachable. If a protection cannot be applied, stop and report the specific failure; do not silently weaken the production unit. OrbStack's laboratory override is not a Pi installation requirement.

## Browser authentication and LAN choices

Start with one explicit access route, not multiple guessed hostnames. The owner must approve a literal bind address, unprivileged port, browser hostname and exact HTTPS origin. The certificate must cover that browser name. LAN DNS/firewall/router changes are separate scope, not implicit installation steps. Avoid wildcard binds and accidental IPv6 exposure. Do not expose raw guest TCP lines, panel RPC or the local approval socket.

For a self-signed certificate, compare its SHA-256 fingerprint through independent trusted access before trusting that certificate on the owner's browser machine. Do not disable certificate verification globally. Record expiry and a stopped-service renewal procedure. Alternatively, use an appropriately issued certificate whose private key remains locally protected. No hosted identity provider or reverse proxy is required.

The writer and observer tokens are distinct role credentials, not per-person accounts. All configured lines share that initial role model. Store tokens privately, enter them only in the password field, and never put them in URLs, shell command arguments, screenshots or logs. Rotation requires replacing the private input and restarting the detached service. A lost or shared token requires deliberate revocation; this milestone does not claim finished multiuser administration.

## Stage 2: separately authorized copied-media guest coexistence

This stage is conditional on owner review of selection evidence and an explicit reversible guest plan. It is **not executable under M5.7 authorization**.

1. Prepare an independently writable disposable guest copy and opt-in profile/unused selection only if separately approved. Preserve the original mappings, images and binaries. Review every profile change; no default boot replacement or forced numeric selection may conceal an unresolved physical selection problem.
2. With the companion stopped, have the owner set the intended physical SR pattern and confirm it. Use Oscar's normal launcher without an override argument only when specifically authorized. Verify the selected profile and copied-media identity before continuing; stop at an unexpected guest.
3. Establish the independent GNU Screen console first. Reserve a separate supported guest terminal line; do not bridge the SIMH monitor, Screen's operator terminal, SSH shell or a listener of uncertain purpose. Independently confirm the guest OS, simulator process/start, boot configuration, copied disk identity, device/line and current listener ownership. These are operator evidence, not an automatic proof synthesized from a port number.
4. Start the companion detached, read fresh local status and explicitly approve that exact instance/line revision. Connect the browser read-only, then explicitly acquire its keyboard. Run a harmless guest echo/listing challenge and verify actual command output separately from local echo.
5. Verify observers cannot type, a competing writer cannot steal ownership, release/handoff is explicit, and reconnect neither replays input nor reacquires a lease. Refresh must retain the chosen endpoint. Select VT100/VT52 only when appropriate for the guest/application.
6. At separate owner-confirmed checkpoints, record physical lamps, HALT and CONT behavior and selector response. Never infer lamp behavior from software. Do not press START or rotary push switches without a separate approved step. Confirm independent Screen commands before and after browser closure and after stopping the **actual companion process**.
7. If a bridge-crash test is included in the future authorization, first idle and synchronize the disposable guest and record only the companion's current MainPID/control group. Terminate that specific companion process; never use broad process-name killing. Verify the guest and independent console remain alive, then restart the companion detached. A guest serial login may hang up even though the CPU continues.
8. Before intentional guest change or simulator restart, stop the actual service and confirm its guest sockets are closed. After the change, independently reverify and approve anew. A surviving TCP stream, familiar banner, PID or reused port cannot establish unchanged guest identity. Do not offer unattended guest following.

Do not claim genuine physical serial/network coexistence unless the owner has the relevant independent guest-supported connection and actually tests it. Unavailable hardware or a missing driver is an untested item, not a passed check.

## Resource measurement plan — future authorization required

Use the unchanged [target table](../roadmap.md#performance-targets). Measure the complete companion process/control group separately from SIMH and the panel daemon. CPU 100% means one core. Capture process start identity to reject PID reuse; use `/proc` CPU deltas, RSS/PSS, control-group CPU/memory/peak/OOM records, listener/viewer counts and timestamped temperature/throttling. The [systemd 257 resource manual](https://www.freedesktop.org/software/systemd/man/257/systemd.resource-control.html) distinguishes control-group limits from process RSS; the 96 MiB unit cap does not replace the 48 MiB active RSS target.

Proposed progression: a five-minute settled detached baseline; one passive browser; one active terminal with a bounded, agreed output rate; two viewers; then a separately approved 30-minute representative workload. Begin small and stop on a failed checkpoint. Eight-observer output is a distinct later workload given the existing CPU exceedance. Record sample duration, workload, rates and raw series; do not choose only favorable intervals.

Keep limits: idle RSS≤24 MiB, active≤48 MiB and peak≤64 MiB; idle CPU<1%; representative active mean<5% and p95<10% over one-second samples; added terminal latency<100 ms p95; guest throughput regression<3%. Isolate transport latency from guest processing/browser rendering. Compare repeatable disposable-guest work with the same emulator configuration and thermal conditions. Owner-observed lamps are functional evidence, not a throughput benchmark.

Stop on new throttling/undervoltage indications, temperature reaching the previously used 70°C pilot threshold, sustained resource exceedance, OOM, stalled independent access or uncertain guest identity. Stop the companion first; do not power-cycle or send guest shutdown automatically. A threshold stop preserves evidence and requires review. No stress or performance run occurs in M5.7.

## Rollback and uninstall acceptance

Prepare these checks before installation. Preserve private records outside managed paths first.

| Action | Required acceptance evidence |
|---|---|
| Stop/disable | Companion inactive and disabled; its HTTPS/control sockets and processes gone; original machine unchanged |
| Release rollback | Stopped companion, verified previous managed release, compatible private config, manual detached start; no guest/media rollback |
| Complete removal | Use the explicit purge option while the managed installation still exists; no unknown files/group memberships/live account processes; remove only companion assets |
| Verify removal | `/opt/pidp11-webdesktop`, `/etc/pidp11-webdesktop`, `/run/pidp11-webdesktop` and its unit absent; dedicated account/group absent; no listener, process, enabled-unit link or unreviewed drop-in remains |
| Original integrity | Approved before/after hashes and metadata agree for original binaries, launcher, maps/profiles and separately authorized media; do not restore a differing file automatically |
| Independent operation | During an approved guest phase, console and owner-observed controls worked with companion stopped; after copied-guest shutdown, original stopped state restored |
| Credentials/trust | Companion credentials revoked/removed; private evidence retained; remove only a specifically installed test certificate trust entry if one was added |

Choose either retention of private configuration or complete purge deliberately. The removal helper refuses unknown content and requires the managed installation marker; do not first remove the installation and then expect a second purge invocation to clean everything. A separately approved guest profile/media experiment has its own stopped-guest rollback and is not deleted by uninstalling the desktop.

Any failed integrity or unexpected-process checkpoint stops cleanup at that point. Preserve evidence and report the narrow recovery action; do not broaden removal, restore disks, restart the launcher or reboot to make the result look clean.
