# M4.1 — Consumer safety and independent access

This milestone is an isolated laboratory implementation, not production control approval. **The Pi was not contacted.** No GPIO, service changes, guest OS images, emulator autostart or production deployment were used. M0–M4 checkpoints and their evidence are preserved.

## Outcome

The original M4 START-release race remains a required failing-safety oracle: the unchanged consumer can execute a delayed falling-edge response after broker revocation. The optional M4.1 consumer interlock rejects that response and rejects stale commands already queued for SIMH dispatch. It also stops managed execution on heartbeat expiry when the consumer can progress. It does **not** establish instantaneous or unconditional halting.

Independent physical-only operation remains the default architecture. The laboratory restores the unchanged SIMH binary, removes the broker from the control path, verifies RPC routing to the physical stand-in, and exercises physical RUN/HALT and a conventional monitor. Two original DZ11 Telnet transport lines coexist independently of browser/panel ownership. That is transport evidence, not an RSX-11M+ multiuser login test, physical serial validation, or a test of the production Screen/SSH setup.

Read [ADR 0004 and the access-independence matrix](../decisions/0004-independent-access.md), [interlock design and state diagrams](M4.1-interlock.md), [browserless rollback](M4.1-rollback.md), and [machine-readable results](m41-report.json).

## Implementation

* Optional consumer authority, monotonic lease watchdog, generation checks around original REALCONS service, bounded single-use command tickets, dispatch validation, and CPU-loop inhibit checks.
* A separate patched laboratory binary. The original source tree and original binary remain available and hash-checked. Unset integration configuration preserves the original path; the same M3 oracle tests that disabled variant.
* Go authority client and optional broker integration. Failed consumer contact inhibits control; a fresh connection never restores ownership. Expired browser renewals cannot revive a lease.
* Explicit fault gates for held RPC replies, queued command dispatch, and heartbeat suppression. These exist only in laboratory entry points.
* One reused UDP receive buffer per serialized client, removing a 64 KiB allocation on every physical poll. The watchdog sleeps until requests or its lease deadline instead of waking at a fixed idle rate. Hot CPU checks are inline and gated off when integration is disabled.
* No new runtime dependency for the Go desktop or browser. The C compatibility module is experimental Linux/POSIX code, not a required web runtime or a production service.

## Acceptance and failure matrix

| Case | Oracle / expectation | Boundary |
|---|---|---|
| Original M4 delayed START release | Original binary still produces a new RUN transition or newly logged RUN command | Counterexample retained, not reclassified as safe |
| Fenced delayed START release | Zero new accepted tickets and RUN transitions after consumer revoke | Consumer generation captured before RPC, checked after response |
| Queued START/RESET, CONT, RUN, DEP, EXAM | Dispatch rejects ticket after revoke | No reversal of an already dispatched synchronous action |
| LOAD ADRS | Held input response cannot mutate loaded address after revoke | LOAD is a direct controller operation, not a queued command |
| Duplicate/reordered/overflow tickets | C unit tests reject duplicates, older sequences and overwritten slots | Bounded 16 slots; conservative rejection may drop actions |
| Previously committed DEP | Memory remains changed after revoke | Deliberately demonstrated inability to undo committed effects |
| Epoch/boot changes | Old PING and tickets cannot renew/execute under new authority | Random boot nonce has probabilistic uniqueness, not a mathematical guarantee |
| Physical/virtual handoffs | Held START inhibits grant; observed HALT/movement revokes virtual owner | Only sampled stand-in levels; no hardware safety claim |
| Browser disconnect/lease expiry | Consumer quiesces; reconnect is spectator | Broker must observe disconnect/expiry before requesting revoke |
| Consumer stall | No false grant/quiescence while stopped; expiry checked on recovery | A stalled process cannot acknowledge safety |
| Independent heartbeat loss | Consumer stops managed CPU even while broker still reports ownership | RPC must remain responsive for observed stop latency |
| Broker crash + lost RPC response | Consumer disarms independently; quiescence can remain false | Original C RPC can block for seconds; no fixed halt guarantee |
| Physical daemon crash/restart | Persistent broker fault, explicit baseline/rearm | No automatic restoration of physical routing |
| Consumer/broker restart | New consumer generation, no owner, HALT baseline | Old sockets removed only after stopped process; no replay |
| Abrupt all-process loss | Restart disarmed; no automatic execution | Volatile-state/power-loss analogue only, not storage/power hardware |
| Original route rollback | Original SIMH + stand-in works without broker/browser/fence | Real physical POWER/LOCK/OS selection remains untested |
| Conventional terminals | Two DZ11 connections + independent PTY monitor | SIGINT stop used; PTY Ctrl-E did not reliably acknowledge in this fixture |
| Malformed/replayed RPC | Existing bounded codec/transport tests plus fuzzing | No malformed traffic sent to physical daemon or Pi |

The test harness now waits for the SIMH startup prompt and the actual WebSocket control revision before issuing the next CAS request. It does not retry rejected mutations. Test-only delays do not widen leases or polling intervals. The original counterexample checks only newly recorded command text, avoiding a stale log match.

## Measured resources and test results

These are short **Mac-hosted Linux ARM64** observations, not Pi acceptance measurements. CPU percentages mean one fully occupied core = 100%. Idle includes real REALCONS and stand-in mediation without WebSocket viewers. Active uses two WebSocket viewers and 300 switch-register writes at 20 Hz, with the guest CPU halted. Terminal throughput is not included.

| Measure | Result | Existing target / assessment |
|---|---:|---|
| Idle broker RSS, mean / peak | 9.39 / 10.36 MiB | ≤24 MiB target; 5-second sample only |
| Active broker RSS, mean / peak | 11.20 / 11.50 MiB | ≤48 / 64 MiB target; 15-second sample only |
| Active broker peak PSS | 9.52 MiB | Reported separately from RSS |
| Idle / active broker CPU | 2.40% / 3.33% | Idle <1% target **not met**; active <5% provisional target met for this small workload |

| Static Go lab executable | 6,160,546 bytes (5.88 MiB) | Production mock executable remains separate; no new runtime module |
| Watchdog stop, responsive RPC | 351.59 ms | One observed sample, not a hard bound |
| Watchdog disarm, lost RPC / broker killed | 298.88 ms | Consumer still reported `quiescent=0`; no stop claimed |
| Patched-disabled CPU-loop benchmark | 4.84% longer median wall time | Three 100M-instruction samples; <3% emulator-impact target **not established** |

The CPU microbenchmark compares original and patched-disabled binaries without RPC, a guest OS or a physical daemon. It is a diagnostic, not a comprehensive guest throughput benchmark. Even with inlined/gated checks it shows measurable overhead; keep the **original binary** for default physical-only operation. Enabled remote-control throughput, sustained thermal effects, packet rates, browser paint latency and 30-minute memory/terminal soaks remain open.

The Mac UDP round-trip allocation benchmark measured roughly 12.3 KiB / 151 allocations per poll with reuse versus 77.9 KiB / 152 allocations with the previous receive-buffer allocation pattern. It measures the whole local test server/client path, resets its synthetic overfull replay cache outside timing, and is not a Pi benchmark. Reusing the 64 KiB buffer removes approximately 3.125 MiB/s of allocation pressure at 50 polls/sec without slowing physical or REALCONS polling. Timing was about 28.3 versus 34.3 microseconds/poll in that short host run; no broad performance claim follows.

Validation completed: original M3 C UDP/TCP/rpcbind/REALCONS oracle; original M4 counterexample and fault suite; patched-disabled M3 oracle; 19 M4.1 scenario results; ASan/UBSan consumer module tests; actual Linux Unix-packet authority tests; `go test -race ./...`; TypeScript check/build, 12 model tests and one reconnect integration test; 10-second RPC fuzzing with **6,018,470 executions**, no crash. Original pinned source hashes and the M0 HTML checksum were checked. The frontend was not visually changed or re-certified across browsers.

## Remaining risk register

| Risk | Current evidence / mitigation | Required follow-up |
|---|---|---|
| In-flight work before revoke commits | Consumer serializes dispatch and revoke; already committed DEP remains | Define operator-visible revoke acknowledgment separately from click/HTTP acceptance |
| Blocking C RPC / stalled execution | Watchdog can invalidate authorization while run acknowledgment remains pending | Bounded/cancellable original RPC or separately reviewed supervisor containment; no automatic resume |
| Privileged console and local host authority | Monitor remains independent and can execute its own commands | Explicit operator coordination; future authenticated capability model, not mandatory web gateway |
| Physical POWER, LOCK, boot selection | Original Mode A retained; optional lab path intentionally neutralizes POWER/LOCK | Source/config/hardware audit before any Mode C proposal |
| Missed edges and stale physical samples | M4 edge-loss test retained; conservative revoke and held-switch checks | Actual daemon sampling/debounce/physical HALT latency measurements |
| Passive observation not implemented | Lab snapshot readers do not mutate controls; additional GET may have side effects | Implement nonblocking publication from original path before authorized observe pilot |
| RPC registration/startup collisions | Rollback explicitly restores both mappings with competitors stopped | Installed startup audit; no two automatic program-99 owners |
| Consumer patch maintenance | Three-file exact-anchor hook patch, separate binary, sanitizer/semantic tests | Review each upstream revision; broader architecture/signal/security review |
| Socket authority and boot nonce | Owner-only Unix socket, bounded packets, random boot generation | Production threat model, peer credentials and durable/cryptographic session identity review |
| Guest persistence / real host shutdown | RAM-only fixtures; abrupt process-loss test clearly labeled | Guest-safe shutdown and media recovery testing in copies, after separate authorization |
| Performance | Short Mac-hosted measurements; idle target remains open | Authorized Pi thermals/guest/terminal workload tests; 30-minute soak and traffic measurements |
| Unsupported access claims | No SSH, Screen takeover, GPIO, real serial or guest network tests | Validate each independently; never infer these from a browser success |
| Formal coverage | Finite oracle tests and invariants, no exhaustive model checking | Independent review/model exploration of all execution paths before production remote control |

## Reproduce and record

```sh
sh lab/build-image.sh
sh lab/verify-m41.sh
go test -race ./...
go test ./internal/labrpc -run '^$' -fuzz FuzzRPCDispatch -fuzztime 10s
npm run check
npm test
npm run test:integration
npm run build
python3 lab/save-m41-results.py
```

The verification sequence runs the original M3/M4 oracle, the patched-but-disabled M3 oracle, M4.1 fault tests, sanitizer-backed module tests and a CPU-loop smoke benchmark. Every emulator process runs inside the existing network-none Linux ARM64 fixture. Artifacts under `.research/lab-results` are copied to new `m41-*` documentation files only after success; M3/M4 historical evidence is not replaced. Source checkpoints and measured binary hashes are retained separately because measurements occur before the final commit.
