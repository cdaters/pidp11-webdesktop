# M5.6 proposal — an optional Web Desktop installation

**Design dated 2026-11-19; not implemented, installed or enabled by M5.5.** A user should eventually be able to power on a PiDP-11 and open its optional desktop from a LAN browser. The web service can become available independently of whether Oscar's emulator has started. It must never start the emulator to satisfy a browser request. Guest availability follows the original installation's own startup policy and the operator's physical selection.

## Package and separation

Distribute one versioned, static Linux ARM64 Go executable with embedded HTML/TypeScript/SVG and lazy-loaded terminal assets. Raspberry Pi OS Lite remains headless. Do not require Node, Docker, a database, a desktop environment or a reverse proxy on the Pi. Preserve third-party notices in the package. Keep conventional SSH, Screen, physical-panel/REALCONS operation and guest disks outside the companion's lifecycle.

Proposed installation paths are `/opt/pidp11-webdesktop/releases/<version>/` for immutable executable releases, `/etc/pidp11-webdesktop/` for private configuration/credentials, and `/run/pidp11-webdesktop/` for temporary state. These are future paths, not claims about the current machine. The companion must have no write access to `/opt/pidp11`, selection maps or guest images. Runtime files must not contain persistent guest-attachment approvals or keyboard leases.

Use a dedicated unprivileged `pidp11-webdesktop` service identity, not the emulator/Screen account. Do not add it to GPIO, disk or administration groups. Any minimal read-only process/socket witness must be separately designed and reviewed; giving the service broad `/proc`, ptrace or sudo access is not an acceptable shortcut. Read-only access to process metadata is not proof of guest identity.

## Startup, stop and upgrades

| Event | Required behavior |
|---|---|
| Install | Verify package/hash, create only companion paths/account, provision secrets, leave service disabled and stopped |
| Explicit start | Validate configuration, bind the approved HTTPS address, serve the desktop **detached**; do not dial a guest |
| Optional owner-enabled boot startup | Start only this web service; an offline guest stays offline; no dependency that pulls in the emulator |
| Browser opens or refreshes | Authenticate and report state; do not start a simulator, select a guest, acquire a keyboard or replay input |
| Service crash/restart | Discard sessions/approvals; restart detached if that policy was separately enabled |
| Explicit stop | Revoke leases and close only companion connections; a guest login may hang up, but no CPU/launcher action follows |
| Upgrade | Operator detaches terminals, stops only the companion, verifies a staged executable, atomically changes the companion release pointer, starts detached and revalidates |
| Failed upgrade | Stop companion, restore its previous binary/configuration version, start detached; never restore or roll back guest disks |

Prepare an ordinary systemd service supervising only the Go process. Candidate policy is `Type=exec`, `Restart=no` for initial deployment, a bounded shutdown timeout, and a separate service control group. No emulator `Requires`, `Wants`, `BindsTo` or `PartOf` dependency, launcher hook, Screen command, RPC registration, startup script, or emulator signal is permitted. A later `Restart=on-failure` policy is acceptable only after detached startup is implemented and tested. These are project design choices informed by the [systemd service documentation](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), not a tested unit file.

Candidate isolation uses `NoNewPrivileges`, `PrivateTmp`, `PrivateDevices`, read-only system paths, a private runtime directory and an empty capability set. Verify interaction with certificate reads and the minimal witness on the actual supported systemd version before packaging. Do not blindly enable a private network namespace: the service must reach the explicitly approved loopback guest line and serve its configured browser address. See the [execution-environment documentation](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html). The consulted upstream manual is systemd 262; it does not establish the installed Pi version or justify using its newest features.

The current `terminal-pilot` executable is **not** this service: it is fixed to loopback and attempts one guest connection during manual startup. M5.6 needs a distinct detached-start lifecycle before any unit or automatic startup can be offered. Keep the guarded lab and supervised pilot entry points intact.

## LAN access and authentication

The first coexistence pilot retains the existing loopback HTTPS plus explicit SSH tunnel. The later LAN option needs a stable owner-approved hostname, exact bind address/port and allowed origin, certificate whose identity matches that hostname, and a documented trust/renewal path. Choose the actual network values during deployment review; do not guess a private host's name, address or firewall. Do not expose the raw guest line or panel RPC as part of LAN web access. IPv6 binding must be explicit, not an accidental wildcard expansion.

Keep TLS/WSS, exact Host/Origin checking, secure HttpOnly SameSite cookies, CSRF protection, expiring sessions, logout, separate observer/input authority and bounded request sizes. Provision unique revocable user credentials outside URLs, command-line arguments, browser storage and logs. Shared pilot tokens are acceptable only for the supervised pilot, not a finished multiuser administration system. Passwordless/passkey or password support requires its own small, reviewed implementation decision; no hosted identity service is required by this design.

Certificate expiry or unreadable configuration must leave the service unavailable or detached with a useful operator error. Never fall back to plaintext, disable certificate validation globally, or connect to another port. Record bounded authentication/lifecycle events without recording passwords, terminal contents or private guest files. Per-user/per-line grants and durable credential rotation remain implementation work.

## Endpoint and guest state

Configuration should allowlist one to four explicit guest lines by opaque ID, friendly profile label, device/line and literal loopback address. Only an independently confirmed, currently reserved line can be approved for attachment. Browser users cannot supply a hostname, host path, SIMH command or OS selection. A profile label means “configured for,” not “guest identity verified.”

The future service needs these separately visible states:

- **Detached:** no guest connection and no permission to open one.
- **Awaiting approval:** a local operator has supplied fresh evidence for one guest/line generation; no keyboard authority exists.
- **Attached, read-only:** one approved connection, fresh renderer, no keyboard lease.
- **Keyboard owned:** a separate authenticated user holds the renewable lease for that attachment.
- **Retired/unavailable:** EOF, uncertain write, changed/stale identity evidence or operator detachment; the old attachment cannot be reused.

Approvals must be bound to a new service instance and guest/line generation, never restored after restart. Browser reconnect to the same still-attached line is distinct from opening another guest TCP connection. Require explicit keyboard acquisition each time; never transfer a lease or uncertain input between guests.

M5.4's one-shot attachment is already implemented. Automatic, authoritative guest identity is not. A reused port, executable hash, PID/start time or login banner does not identify a new boot within the same simulator process. For the initial installed mode, stop/detach the bridge before intentional guest changes, verify the new guest through the independent operator, then approve a new attachment. Do not promise unattended guest following. Automatic detection requires the separately reviewed lifecycle evidence described in [M5.4](M5.4.md); a delayed watcher cannot recall bytes already delivered.

The desktop must distinguish its simulated front panel/peripherals from actual guest terminal output. A disconnected terminal must not imply that the CPU halted. Passive panel observation remains a separate opt-in future component with no input polling or control authority.

## Resource budget and acceptance

Retain bridge targets of ≤24 MiB idle RSS, ≤48 MiB active RSS, ≤64 MiB peak RSS; <1% idle and <5% mean active CPU of one core; and <100 ms p95 added terminal transport latency. Use the Pi 3B+'s 1 GB hardware budget, measuring actual available Linux memory. Keep existing bounds: at most four endpoints, eight viewers per endpoint, 64 KiB unacknowledged output per viewer, 256-byte input operations and 10-second keyboard leases. A slow viewer is disconnected instead of growing queues or blocking the original emulator.

Measure the whole service control group as well as process RSS/PSS, TLS buffers, open sockets and browser-side memory. Candidate memory accounting and a provisional 96 MiB service limit need workload validation; a control-group limit is not the same measure as process RSS. Do not set a CPU quota so tight that it delays lease handling. Resource exhaustion must affect the companion only, not place SIMH in the same control group. The [resource-control manual](https://www.freedesktop.org/software/systemd/man/latest/systemd.resource-control.html) describes these mechanisms; the values here are proposed project limits, not passed performance results.

M5.6 acceptance requires a disposable installation rehearsal first: install disabled, start detached with guest absent, provision/revoke credentials, exercise certificate expiry and incorrect origin, restart/crash without guest attachment, upgrade/rollback, disable/uninstall, and verify original files and independent access after each transition. Actual Pi acceptance then needs separate authorization, sustained workloads and power/thermal observations. M5.3's short standalone numbers and the [M5.5 physical pilot](M5.5-physical-pilot.md) do not establish sustained LAN/service performance. M5.5 recorded a 5.55% short active bridge CPU sample and failed its physical-only fallback selection; resolve those open gates before claiming accepted integration or deploying this service.

## Disablement and uninstall

The future owner-facing procedure should stop and disable only `pidp11-webdesktop.service`, confirm its listeners have closed, and show that Screen and physical operation remain usable. Uninstall removes the companion unit, release directories, runtime files and its dedicated account only after checking for retained owner files and other account uses. Revoke/delete companion credentials and its unused certificate material. Preserve explicitly requested audit/configuration backups privately.

Do not remove Oscar's installation, original services, RPC infrastructure, guest profiles/media or any optional pilot profile as an incidental uninstall step. Profile retirement has its own stopped-guest, preserved-media and selection-map rollback procedure. The disabled companion must leave a complete physical-only PiDP-11.
