# M4.3 browser retention investigation

2026-11-17. Chromium on the Mac; all terminal output is a local mock. This investigation preserves a failed resource check and distinguishes application cleanup, visible DOM size, native browser editing history and JavaScript heap. It is not Pi memory acceptance.

## Initial measurement and failed budget

The first 1,800.03-second run completed 1,440 mock commands, 30 terminal close/reopen cycles and 30 media cycles without JavaScript errors. Retained JavaScript heap was 5,573,964 bytes, below the 64 MiB limit. The retained node count increased from 2,181 to 4,192: **+2,011, failing the +2,000-node check**. The test exited unsuccessfully; `browser-soak-initial.json` retains its measurements. Neither zero console errors nor a small heap makes that original budget check pass.

## Investigation

A separate final-artifact test created, exercised and disposed a terminal 60 times, issuing 600 commands. After disposal, connected elements remained at 727 and event listeners at 139. Post-GC total nodes changed from 1,689 to 1,692. This supports correct cleanup for that workload; it is not a proof against every possible leak.

Lazy mounting was considered as a baseline explanation. Three comparisons of immediate, rendered and settled four-terminal startup showed only small node differences. That hypothesis does **not** explain the roughly 2,000-node increase. The timing/readiness improvement remains in the harness, but is not claimed as an application leak fix.

An accelerated diagnostic sampled garbage-collected metrics and the connected DOM. Connected element count remained stable while total browser nodes grew. A heap snapshot after 600 commands contained 465 native `blink::UndoStep` instances, 1,860 `InsertIntoTextNodeCommand` instances, 465 insert-node and 465 remove-node commands, and 469 textarea placeholder breaks. The checked-in summary includes the full local heap snapshot's hash; the bulky heap itself stays in the ignored research directory.

The existing xterm renderer has screen-reader mode enabled. Its public source explains that ordinary input events are allowed to update the accessible textarea so assistive technology can announce input. Chromium retains native editing history for such fields. The inspected upstream [UndoStack implementation](https://chromium.googlesource.com/chromium/src/+/4852d4ffeefa31265675175f00edcf84c5e30ecd/third_party/blink/renderer/core/editing/commands/undo_stack.cc) caps its history at 1,000 undo steps. This source and the heap evidence explain the growth; the accelerated plateau experiment separately checks whether the tested workload stabilizes. A source limit is not a guarantee for arbitrary future browser builds or inputs.

No upstream xterm code, browser settings or accessibility support was changed. Clearing browser editing history through private APIs or suppressing accessible input merely to obtain a lower number would not establish healthy application behavior.

## Final measurement contract

The final timed browser workload starts after all four terminal banners render and **40 warm-up HELP commands** exercise their input/rendering paths. The full 1,800-second measured interval follows that warm-up. It retains the same 64 MiB heap and +2,000-node growth thresholds; warm-up commands are recorded separately from measured commands. This is a warmed-workspace stability measurement. It does not retroactively pass the original startup-to-finish budget or claim zero initial allocation.

The extended accelerated diagnostic (`scripts/m43-browser-plateau.mjs`) uses 5,760 commands and 120 terminal/media cycles to inspect the plateau, with explicit post-GC samples. It reports the original cold-growth budget separately from a steady-state check (node/connected-element range no more than 50 after the first 1,800 workload steps, and retained heap below 64 MiB). Passing the latter never changes a failed cold-growth result. It is not another 30-minute wall-clock soak, and its timing must not be interpreted as a 30-minute benchmark. The first temporary accelerated record also inherited a CPU divisor and concurrent-lab scope string from the timed harness; those fields are inapplicable to that diagnostic. The committed runner omits those misleading fields and states its own scope. The final timed result and measurements are in [performance](M4.3-performance.md). Retain these distinctions when interpreting future browser/renderer changes.

## Recorded accelerated plateau

The committed diagnostic completed in 435.53 seconds, with 5,760 commands and 120 terminal/media cycles. After its first 1,800 workload steps, post-GC total nodes stayed within **4,213–4,226**, and connected elements within **1,004–1,007**. The steady-state check passed; the separately reported initial +2,000-node budget still failed. This is evidence of bounded node retention for the tested workload, not proof of unlimited runtime stability or a claim that every browser cache is fixed-size.
