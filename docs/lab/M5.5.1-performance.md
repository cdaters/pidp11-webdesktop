# Terminal performance investigation — M5.5.1

November 19, 2026. **No physical Pi benchmark or access.** M5.5's historical 20.01-second active-browser sample was 5.5469% of one core, rounded to 5.55%, with 14,176 KiB maximum sampled RSS. It exceeded the unchanged <5% active CPU target, but did not identify a persistent regression or its cause. The current work does not retroactively pass that gate.

## Two measured, focused changes

The secure access gate previously parsed its immutable configured origin every time it checked the request Host. It now stores the validated host at construction. Exact Host, TLS, Origin, cookie, expiry, capability and revocation checks remain in place. The origin microbenchmark dropped from a median 102.9 ns and one 144-byte allocation per check to 2.243 ns and zero allocations on the Mac. This isolates one check, not the whole authentication path, and its small absolute cost is not an explanation of the Pi's CPU sample.

The guest reader previously copied each output chunk once **per viewer**. It now makes one immutable copy shared by the output frames, preserving independent credits, queues and disconnect decisions. No caller mutates these bytes. Stale-reader checks still precede publication; no polling interval, lease duration, write deadline or output bound changed.

| 1 KiB fan-out microbenchmark | Before, median ns/op | After, median ns/op | Before → after allocation |
|---|---:|---:|---|
| One viewer | 675.4 | 677.9 | 1,024 → 1,024 B; 1 → 1 allocation |
| Four viewers | 1,065 | 786.7 | 4,096 → 1,024 B; 4 → 1 allocations |
| Eight viewers | 1,564 | 918.3 | 8,192 → 1,024 B; 8 → 1 allocations |

Three runs each used Go 1.26.0, darwin/arm64, Apple M4 Pro. The fan-out test includes net.Pipe scheduling and returns every viewer's renderer credit. It excludes TLS, JSON encoding, network hardware and browser rendering. [Before](m551/bench-before.txt) and [after](m551/bench-after.txt) records are retained. The single-viewer result is essentially unchanged; do not claim a universal speedup.

Inspection found bounded WS frames, disabled compression, per-message authentication/ownership checks, explicit renderer acknowledgments, a 100 ms lease tick and 500 ms WS permission check. Renewals update the lease without broadcasting a new state to every observer. Those protections were retained. JSON/base64, TLS and per-viewer delivery still have real costs. This milestone does not trade safety checks for throughput or introduce a binary protocol rewrite.

## Repeatable Linux service workloads

The final package ran under systemd 257 in a disposable Debian 13 ARM64 environment on the Mac, kernel `7.2.12-orbstack-00394-gbecdd6130068`. Creation requested two CPUs and a 1 GiB environment limit; `/proc/meminfo` exposes OrbStack's larger shared-kernel memory inventory, **not** a 1 GB Pi's available memory. The web service had its separate provisional 96 MiB cgroup ceiling. There was no emulator in the measured service environment.

`lab/m551/transportbench` authenticated using the actual TLS/cookie/WS path and explicit local attachment approvals. It measured the service's `/proc/PID/stat` CPU delta (Linux USER_HZ 100; 100% means one core), sampled process RSS approximately every 50 ms, and excluded the synthetic peer/client process's CPU. Scenarios ran sequentially in the same service process for 30 seconds each, after an initial six-second exploratory matrix. Memory is therefore cumulative/GC-dependent; this is not nine fresh-process cold-start comparisons.

[Raw 30-second results](m551/linux-performance-30s.json). Input and command-sized strings were echoed by a synthetic TCP peer; they were not executed as PDP-11 commands. The echo latency includes client JSON/TLS/WS, bridge, synthetic loopback transport and return path, but excludes actual browser rendering and historical guest processing. There were 572, 1,136 and 572 echo samples in the respective active/burst cases. A zero latency field in raw JSON denotes an unmeasured scenario, not instantaneous delivery.

The eight-observer case remains over the numeric 5% CPU budget even here. It is also heavier than the original acceptance workload of two viewers and a 10 KiB/s terminal. Report it as a scaling limit requiring further measurement, not as either a passed Pi target or proof that the original representative workload must fail. No target was raised.

## What remains open

Retain ≤24 MiB idle RSS, ≤48 MiB active RSS, ≤64 MiB peak RSS; <1% idle and <5% mean active CPU of one Pi core; and <100 ms p95 added terminal latency. The actual Pi acceptance also needs the specified settled/long-duration workloads, PSS/cgroup accounting, one-second CPU distributions, emulator-throughput comparison, browser memory, power/temperature and throttling observations. Those were not measured here. Thirty-second Mac-hosted results are reproducible engineering evidence, not sustained Pi acceptance.

A future separately authorized performance run should first resolve switch selection, preserve a known guest identity, measure the whole companion service and emulator separately, use the same repeatable workloads, and retain raw samples. First optimize only a demonstrated remaining hot path. Eight-viewer JSON/base64/TLS fan-out merits profiling before considering shared serialization or a protocol change; neither is implemented by this report.
