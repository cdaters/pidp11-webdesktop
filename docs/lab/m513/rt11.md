# RT-11FB reproduction and terminal-status diagnosis

M5.13 uses a new writable copy of the same verified RT-11 disk, original SIMH and
original guest sources/tools. No physical machine or preserved original disk was
modified. Base SHA-256:
`543277ee81fb4c024d19242bf6d6a04c81a257c48fe4cece256a42de3fe8dd98`.

## Exact generation choices

The supplied disk boots RT-11SJ (S) V05.03. `IND SYSGEN` identifies V05.52 and
produces V05.52 conditional/batch files with 1986 notices. The generated monitor
still identifies RT-11FB (S) V05.03. These observed versions must not be represented
as a complete matched-release distribution. The reviewed July 1984 V5.1 System
Generation Guide is earlier still; it supports the general MTTY distinction but
is not proof of every V5.3 implementation detail.

[`rt11-sysgen.py`](../../../lab/m513/rt11-sysgen.py) reproduces the observed prompts
and refuses unknown ones. Its new answer-file name is `M513.ANS`. Choices:

| Area | Choice |
| --- | --- |
| Monitor | SJ no, FB yes, XM no; system-job support yes |
| Multiterminal | Yes; asynchronous status and timeout yes; device timeout automatically enabled |
| Buffers/clock | Output 40, input 134 bytes; 60 Hz; other listed monitor questions accept recorded defaults |
| Disk | DL only, two RL units; no custom handler or extra slots |
| Console | One local DL including console, no remote DL; CSR 177560, vector 60 |
| Additional line | One DZ11 multiplexer, one local line, no remote lines; CSR 160100, vector 300 |
| Line format | 9600 baud (`DZSP$D=7000` octal), default stop unit `DZST$P=0` |
| Work files | Sources, binary output and maps on disposable SY; retain objects/work files |

`@M513.MON` builds original monitor modules and `RT11FB.SYG`; `@M513.DEV`
builds the matching `DL.SYG`. A separately named `M513FB.SYS` and `M513DL.BAK`
preserve the working disk's previous handler. The preserved original base is
never mounted writable.

A reproduction failure clarified an omitted ordering requirement: replacing
`DL.SYS` on the working disk and restarting its unchanged default SJ bootstrap
causes `?BOOT-U-Conflicting SYSGEN options`. A subsequent `BOOT M513FB` entered at
SIMH's prompt is not an RT-11 command and failed without starting the monitor.
Both records are retained. Recovery booted a **new disposable baseline copy** as
RL0, attached the generated working disk as RL1, and issued `BOOT DL1:M513FB`
from RT-11. That succeeded with the matching monitor/handler. This rescue-copy
sequence is the reproduced route; a direct replacement bootstrap is not claimed
tested. Keep the original bridge stopped throughout any such transition.

`SHOW CONFIG` then reported multiterminal support; `SHOW MEMORY` reported RMON
5967 words and DL 488 words. Original MTTEST was assembled with
`MACRO/OBJECT:MTTEST M513.CND+MTTEST`, then linked, without editing its source.

## Measured discrepancy, not a presumed driver defect

The original V3-era MTTEST creates expected terminal status blocks in `TSB`. It
expects the second configuration word to be zero, described there as unused.
Its `.MTGET` comparison reports the same terminal-status error for either of the
first two words, so the printed message alone cannot locate the disagreement.

The new original RetroRealm [MTSTAT.MAC](../../../lab/m513/MTSTAT.MAC) attaches
LUN 1, reads its four words, prints them in octal, detaches and exits. It does not
change terminal status or replace the historical diagnostic. Observed values:

| Word | Returned | Interpretation from installed source |
| --- | --- | --- |
| 0 | `007202` | 9600-baud setting plus normal CR/LF and page bits; matches MTTEST expectation |
| 1 | `000003` | Installed `TRMTBL.MAC` initializes DZ word 2 from `(DZST$P + 030) / 010`, explicitly including eight-bit character length |
| 2 | `000000` | Fill character/count |
| 3 | `010120` | DZ terminal-state flag and 80-column width |

The initial 300-versus-9600 hypothesis was rejected: the generated conditionals
supply `DZSP$D=7000` to MTTEST. The measured discrepancy is word 1, where MTTEST's
older expectation is zero but the installed table intentionally sets three.
No driver patch or altered expected value was used to obtain a passing diagnostic.
The full original diagnostic therefore remains **not accepted**; the failure is
now explained at source/returned-value level.

## Application and lifecycle evidence

Chromium connected through the actual Go bridge and original DZ line. MTTEST read
and retyped `M513 BROWSER LINE`, in addition to terminal echo. Reconnect began
read-only. Its asynchronous special-mode test echoed lowercase and digits; its
second asynchronous test reported input-available ON then OFF for a completed
input line. The original console terminated both phases with its documented
control-C mechanism. After stopping the actual bridge, `SHOW CONFIG` still worked
through the independent console, followed by simulator exit at idle KMON.

Early extension harnesses incorrectly expected a line-mode input event before
Enter, looked for the wrong message wording and read only a new IPC slice after
asynchronous output had already arrived. Another sent before the application had
finished its preceding output phase. The corrected harness waits for the actual
phase, supplies Enter in line mode and observes only newly appended console
records. Failed attempts remain separate; they were not silently counted as passes.

| Acceptance level | M5.13 result |
| --- | --- |
| Generated monitor / matching handler boot | Pass via explicit disposable rescue boot |
| Original console | Pass, including after actual bridge stop |
| Separate serial application / browser | Pass through original DZ11 |
| Application I/O | Line echo plus retype; lowercase special-mode echo; asynchronous input flag |
| Independent monitor commands on DZ line | Not established; no independent shell/login claim |
| Full original MTTEST | No; explained version-dependent status-word mismatch remains |
| Reconnect | Read-only; explicit keyboard reacquisition |
| Broad fault/recovery qualification | Not claimed; controlled bridge-stop/console/exit subset only |

The reviewed guide describes programmed I/O, not one KMON per serial line. An
independent command environment would require additional suitable software and
its own qualification; neither a successful MTTEST nor a new socket supplies it.
