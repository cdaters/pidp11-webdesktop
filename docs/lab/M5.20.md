# M5.20 — Genuine printer and paper-tape workflows

Completed on 2026-11-23 UTC in disposable Mac-hosted ARM64 Linux. This is development
main, not a new release, owner acceptance, or physical installation qualification.
No Pi, SSH, GPIO, original launcher, website, upstream repository or model service
was contacted. The [private backup summary](../../lab/m520/results/backup.json) was
verified before implementation or new guest work began.

## What now works

RSX-11M-PLUS V4.6 BL87's installed **PIP M2101 (ANSI)** utility printed 160 records
through its LP11 driver. The text was entered through the real browser terminal;
the browser printer displayed actual original-SIMH output and downloaded the exact
completed file in Chromium, Firefox and WebKit. A second fresh RSX instance copied
a disposable paper tape through its installed reader and punch drivers. Its
completed 725-byte artifact also downloaded identically in all three engines.

A separate diskless PDP-11 program transferred every byte value through PC11 in
three phases. This preserves the distinction between an operating-system utility
and CPU/device-only qualification. Neither is a physical Pi test.

The existing **Line printer** and **Paper tape** windows now offer explicit **Local
simulation**, **Observe device** and **Completed exports** modes. Simulation remains
the default. Switching modes cancels the previous observer; no selected producer,
keyboard authority or connection is restored implicitly. Source details describe
operator-attested identities and the limits of observation. The browser cannot
select host paths, mount media, invoke SIMH commands or renew producer authority.

## LP11: browser terminal to actual printer bytes

Before boot, the private harness enabled LPT and attached a new empty disposable
spool. The guest used the original 11/70 CPU with 4 MiB, RQ0 working disk and DZ11
application line. A separately started Go bridge was explicitly attached only after
both guest startup completion and the conventional application-line prompt were
verified. A separate local supervisor approved the fresh printer producer and
renewed its five-second lease while the exact simulator process remained present.
OS identity remained an operator attestation, not a process-detection claim.

In the **RSX browser terminal**, after explicit keyboard acquisition:

1. `PIP M520LP.TXT=TI:` created a new file on the working disk.
2. Each of 160 authored records was reviewed as a paste and submitted with a
   separate Enter. Ctrl-Z ended input. Record 001 was
   `M5.20 RSX LP11 ROW 001 - PIP THROUGH THE ORIGINAL LPDRV DRIVER`.
3. `PIP M520LP.TXT/LI` listed `M520LP.TXT;1`, 20 blocks.
4. `PIP LP:=M520LP.TXT` returned to PIP's caller prompt without a PIP/MCR error.

The browser observed **8,192 host-visible bytes** while the original simulator
still held buffered output. Its completed-download button remained disabled.
The saved incomplete prefix was exact, SHA-256
`936708bfdc05daa048cefc53058266860319b52bf5bd84c1b042d2164bd59be9`.
A pause in output and a returned prompt did not by themselves complete observation.

After independent conventional-console inspection of task state, the private lab
operator paused the simulator, verified LPT CSR `000200` (ready, no error) and POS
**10,241 decimal**, detached only the now-idle LPT and resumed the guest. This
specific, supervised close flushed the file; it is not a browser operation or a
recipe for detaching a busy guest device. The supervisor then approved completion
with the independently verified full-file checksum.

The actual transformation was one leading FF, followed by **LF + record + CR**
for each of the 160 records. Every record was compared with the separately retained
input list. The full 10,241-byte output SHA-256 is
`706f20f081598b6834338580165df8bbf981a8fe749a50d81143fc0066a6a8f1`.
All three browser downloads matched. See [byte checks](../../lab/m520/results/printer-bytes.json)
and [browser checks](../../lab/m520/results/printer-completed-browsers.json).

Paper rendering preserves CR/LF/FF/BS semantics separately from raw downloads.
A leading FF really produces a blank first form; use Latest output to reach later
ink. Paper width/scrolling is presentation, not an injected printer-driver wrap.
Text downloads preserve the original ASCII control bytes. No automatic print-job
boundary, spooler queue or printer sound was introduced.

## PC11: two distinct qualifications

### Diskless CPU/device transfer

The private producer attached a verified read-only working input containing bytes
0–255 repeated 48 times. Original PDP-11 instructions polled PTR/PTP registers and
copied three 4,096-byte phases. Chromium observed the first phase, Firefox the
second and WebKit the final phase. Incomplete downloads matched their exact prefixes;
completed download stayed unavailable until explicit completion. PTR positions were
4,096, 8,192 and 12,288 decimal. An additional read produced CSR `100000`, establishing
actual end-of-tape. Only then were reader progress/EOF reported separately and the
closed punch file marked complete. Reader EOF alone never completes a punch job.

Input and output were both 12,288 bytes, SHA-256
`8dec5fb0de8a0b457c0cf7be559e4ef488e9cf39d5ddb0ff7464b23372ab21fa`.
The reader snapshot also matched. [Phase results](../../lab/m520/results/cpu-pc11-phases.json)
and [browser results](../../lab/m520/results/cpu-pc11-browsers.json) label this
**CPU/device-only**, not guest-driver evidence.

### RSX reader/utility/punch

A second independent RSX working disk booted with PTR and PTP attached before boot.
Input was a read-only disposable 401-byte tape: 16 NUL leader bytes, 12 authored
CRLF records (`M5.20 RSX PAPER TAPE RECORD 01` through `12`) and a final SUB byte.
Input SHA-256 was
`ef24164931c24825ef990c46a3280e33e1b9697a108702927d0bfab89f136d9b`.

The **independent RSX console** executed `PIP PP:=PR:` and returned to its prompt.
After that safe boundary, the private harness paused the CPU: PTP CSR `000200`,
POS 725; PTR POS 401, CSR `100000`. It closed PTR/PTP and resumed the guest.
The output preserved all 12 records, CRLF and SUB; the input's 16-byte leader was
replaced by 170 NUL bytes and another 170 NUL bytes followed the records. That
observed transformation was independently checked against the original fixture.
It is a finding about this installed driver/utility and fixture, not a universal
RSX tape-format rule or binary-copy claim.

Output: **725 bytes**, SHA-256
`8ad18e40c82fc9db2268231ab881695402f3b15fed8d089613abbe5d2d08995d`.
An attempt to approve the already-written spool as a live follower was correctly
refused: fresh empty spool required. The file was instead explicitly approved as a
completed export after close/hash verification. All three browsers downloaded the
exact artifact through the existing Paper tape window. See [transformation](../../lab/m520/results/rsx-pc11-bytes.json)
and [downloads](../../lab/m520/results/rsx-pc11-browsers.json).

This is real OS-driver I/O with completed browser export. It does **not** qualify
live streaming while RSX punches, browser-originated reader selection, arbitrary
binary PIP copy, tape swapping or a safe unattended media supervisor. The CPU test
separately exercises live progress and all eight data bits.

## Lifecycle, limits and testing

Frontend validation now binds selected device ID, type, simulator and guest
identity as well as generation. Reader hash/length cannot change mid-observation;
progress cannot retreat and EOF cannot disappear. Changed metadata stops the
observer. LP11 high-bit bytes are refused. Closing/switching modes cancels requests,
and late responses cannot repaint the replacement window. Network failure retains
available bytes with an incomplete label and no automatic reconnect.

Live downloads identify retained incomplete ranges and their generation. Completed
exports provide original bytes and, for LP11, text. Existing bounds remain: four
devices, 1 MiB live job, 64 KiB retained tail, 8 KiB per poll, 200 ms poll scheduling,
64 KiB reader/completed snapshots, and five-second producer approvals. The Go bridge
still has no simulator supervision, media-write or mount authority.

[Validation summary](../../lab/m520/results/tests.json):

- Go vet and uncached race tests: pass, 22 packages with tests. New cases cover
  reader EOF versus punch completion, expiry while the original writer continues,
  wrong reader hash, oversized/symlink input and invalid LP11 bytes. Existing
  truncation/regrow, missing-byte, renewal, generation, slow-reader and shutdown
  cases remain in the passing suite; these are fixtures, not all real-guest faults.
- TypeScript validation, build, 105 frontend units, one transport test and nine
  selection-contract tests: pass. The existing large-bundle build warning remains.
- Full browser regression: **153 passes**, no skips/failures/flakes, three engines.
  Final small visibility/overflow changes then passed **45 affected cases** across
  all engines. Earlier focused runs passed 36 and 33 cases; these overlap and are
  not additional unique coverage. Final assertions include hidden printer-only
  controls in the punch view.
- Genuine evidence: one Chromium guest printing run, one Chromium partial-printer
  recovery, three completed LP11 downloads, three CPU PC11 phases and three
  completed RSX PC11 downloads. These are separate from intercepted browser fixtures.
- Python helpers parse, JavaScript helpers syntax-check, artifact transformations
  independently reverify. The corrected whole printing script was not replayed.

The real LP/CPU runs used implementation checkpoint `ed0d970`. RSX completed-tape

changes hid printer controls in tape views and allowed vertical overflow; their
45-case fixture validation did not restart a genuine guest experiment.

These are short idle observations after the workflows, not active-load percentiles,
Pi figures or proof of every memory budget. [Raw aggregate fields](../../lab/m520/results/resources.json)
are retained. There was no new end-to-end latency benchmark; the 200 ms poll schedule
does not bound original stdio buffering, network delays or browser scheduling.
Retain targets of ≤24 MiB idle RSS, ≤48 MiB active/≤64 MiB peak, <1% idle/<5% mean
active CPU of one core, and ≤100 ms p95 terminal round-trip for later representative
qualification. The 96 MiB enforced ceiling with zero swap remains a physical gate.

Failures and corrections are recorded rather than silently converted into passes:

- The backup preflight lacked space at its first location; the owner supplied the
  NAS destination. An ACL-reader assumption and unpadded-base64 verifier error were
  corrected with retained evidence before successful full archive readback.
- The first conventional-line probe read only CR/LF and failed to prove a prompt.
  A full bounded probe later established the prompt before attachment. A shell
  sequencing mistake allowed setup attempts to continue after the first failure;
  neither started a bridge. Later dependent setup used fail-fast sequencing.
- Copying into the read-only container root failed, then execution from temporary
  storage was refused by its no-exec mount. The binary was placed in the owned
  working mount; isolation flags were not weakened. A later doubled `/lab` path
  failed before provisioning and was corrected without restarting the guest.
- The guest print completed, but the test's Stop-observing click was obscured by
  the foreground terminal. That run failed in browser cleanup. The saved prompt
  proved printing had returned; a separate read-only recovery observed/downloaded
  the existing job. The corrected script raises the right window and was not
  rerun against the already-used guest filename.
- An initial guessed CRLF/trailing-FF transform did not match printer output. No
  completion was submitted until the actual leading-FF/LF-record-CR structure
  matched all separately recorded inputs.
- The nonempty live-spool approval refusal described above was expected safety
  behavior. Completed publication used its distinct, existing API.

Original ARM64 exit-139 incidents, V7 plotting timeout and BSD robots initial redraw
remain unresolved. No recurrence here is a fix. Independent security review,
operator-attested guest identity, upstream interoperability agreement and physical
readiness remain separate limits.
