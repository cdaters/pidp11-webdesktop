# M5.7.2: supervised ADDRESS-lamp comparison

**Completed November 19, 2026, America/Phoenix.** The original physical panel/REALCONS path reported SR0 asserted with its paddle DOWN, UP and DOWN again. SR1 responded in both directions while SR0 remained asserted. The owner observed matching ADDRESS lamps after each LOAD ADRS operation. The diagnostic has stopped and cleanup passed; the Pi remains powered on, all SR paddles DOWN and HALT down. No guest operating system or Web Desktop ran, and no hardware-acceptance tag was created.

## Physical results

The owner approved one verified diskless startup and confirmed exclusive maintenance. Initially all numbered paddles were DOWN; the labeled controls were described as centered, without inferring HALT's electrical state. The owner then operated HALT: RUN went dark and ADDRESS/DATA activity stopped. The original console reported `Simulation stopped`. CONS PHY was already selected, so no ADDRESS-selector movement was necessary.

Every subsequent switch movement and LOAD ADRS operation had its own owner checkpoint. The console reading followed the owner's lamp observation; no standalone scanner or extra panel-input RPC client ran concurrently.

Console values are octal. RUN was explicitly confirmed dark after B, C, D and D return. For A it was confirmed dark before LOAD ADRS and reconfirmed before B. The final owner response called the lamps “SR1” and “SR0” in answer to the ADDRESS-lamp question; the table records them as ADDRESS lamps, preserving the distinction from the switch paddles. Raw owner responses and console transcripts are retained privately. [Sanitized physical results](m572/physical-results.json).

Before Test A's LOAD ADRS operation, the owner reported ADDRESS lamps 1–4, 6 and 16–21 lit. This was the pre-load display, not a measurement of all-DOWN SR. After LOAD ADRS, only ADDRESS lamp 0 remained lit; PARITY LOW was also lit. The original source computes PARITY LOW/HIGH from simulated memory-data bytes during reads and clears them on writes. PARITY LOW alone is not a parity-error indication or an electrical reading of SR0.

A duplicate Test A prompt was delivered across a conversation continuation. The owner explicitly confirmed the operation was already performed; it was not repeated. Photographs were requested, but none were supplied for review. These are owner-reported physical observations corroborated by console readings, not photographic evidence.

## What the comparison establishes

The five console values were **1, 1, 1, 3, 1**. SR0 did not change in the captured DOWN–UP–DOWN observations. SR1 added and then removed its bit while SR0 stayed asserted, so the display and acquisition path were not simply frozen at 1. This agrees with [M5.7's all-DOWN scanner readings](M5.7.md) and [M5.7.1's UP/DOWN comparison](M5.7.1.md).

The standalone scanner and running panel daemon use different acquisition schedules over the same physical matrix. Agreement makes an explanation confined to the standalone scanner less persuasive. It supports investigating SR0's contact and signal path, but does not prove a defective switch, solder joint, GPIO input or any other specific component. Shared electrical, initialization or mapping causes remain possible. The captures do not measure voltage, contact continuity, debounce behavior or intermittent transitions between observations.

The original source preserves bit 0 during LOAD ADRS, and CONS PHY displays the loaded address while halted. The isolated original-C rehearsal also produced zero from synthetic SR zero. Those findings argue against an inherent REALCONS rule that forces ADDRESS bit 0 on. SR1's response further argues against a generally stale display. Neither finding proves the physical circuit correct.

## GPIO, privilege and timing boundaries

The original daemon multiplexes LEDs and scans switches. It drives LED rows GPIO20–25 and shared columns GPIO26,27,4–13, changes those columns to inputs for switch scanning, and drives switch rows GPIO16–18 low in sequence before returning them to input. These are BCM GPIO numbers. Its requested switch-row pause is 0.5 µs; the standalone scanner requests 10 µs without lamp multiplexing. Neither is a measured electrical settling time. The daemon records high column levels and inverts active-low slices into logical SR values. This is a separate acquisition path, not an independent electrical instrument.

Both binaries were verified to have ordinary-user IDs and `NoNewPrivs=1`. The existing account already had GPIO access. The original rotary-push path can invoke restart/shutdown helpers, so those controls remained untouched. `no_new_privs` prevented descendants from obtaining privileges through setuid execution, including the shutdown helper's `sudo`; it was not a general sandbox or a change to original logic. [Linux privilege semantics](https://docs.kernel.org/userspace-api/no_new_privs.html).

A diagnostic-created `/dev/shm/pidp11/tmpsimhcommand.txt`, absent before startup, contained only `quit`. It gave the original POWER callback a bounded exit command if reached unexpectedly; no such callback was observed. The file still contained `quit` at cleanup and was removed after the owned processes stopped. The preexisting containing directory was preserved.

The key position was not separately reported; no key movement was requested. Source review shows this daemon's PANEL_LOCK value is internal/startup-controlled rather than a physical key input. START, CONT, DEP, EXAM, rotary pushes and key changes were not used. No REALCONS TEST or DEBUG mode was enabled, and no GPIO restoration command was invented after daemon exit.

The daemon emitted `warning: failed to set RT priority`. The original source treats this as nonfatal; retained M5.5 original-launcher logs contain the same warning. Its threads used normal time-sharing scheduling. No priority setting was changed, and these results do not establish real-time timing performance.

## Justified next inspection and M5.8 status

A **separately authorized, powered-off inspection** of SR0 is now justified. The existing [M5.7.1 inspection proposal](M5.7.1.md#interpretation-and-next-hardware-inspection) remains the procedure for review:

1. Record the PCB revision and front/rear photographs before deciding on disassembly. Compare SR0's labeling and mechanical travel with the now-observed responsive SR1; do not infer contact continuity from paddle position.
2. Before opening the assembly, touching connections or measuring resistance, arrange an authorized normal Linux shutdown, disconnect all power sources and verify the assembly is unpowered. Nothing in this report authorizes those operations now.
3. Use the assembly guide and schematic for that exact PCB revision to inspect the SR0 contact, orientation, associated joints and row/column path. The scanner maps SR0 to BCM GPIO16/26; these numbers are not physical header pin numbers or sufficient probe-point instructions.
4. Only with identified points, suitable equipment and separate approval, compare unpowered SR0 contact behavior in both positions against SR1. Stop if the schematic, access or readings are uncertain. Do not solder, replace parts or probe live voltage based solely on this report.
5. Propose any repair from actual inspection evidence. Reassembly, power-on and another bounded scanner/REALCONS test need their own authorization; an original guest is not needed to verify a repair.
