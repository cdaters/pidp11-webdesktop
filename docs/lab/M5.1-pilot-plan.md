# Proposed first Pi terminal pilot — not executed

**Later result:** [M5.3](M5.3.md) records the authorized standalone terminal pilot and cleanup. The text below preserves what was known/proposed at M5.1; it is not a claim that the pilot remains unexecuted.

Prepared 2026-11-18 from the [M5.1 read-only assessment](M5.1.md). **Owner review and explicit approval are required before any Pi file creation, deployment, guest start, listener attachment, service action or tunnel in this plan.** M5.1 authorized inspection only. The accepted M5.0 laboratory command cannot be deployed unchanged because it deliberately rejects a normally networked host.

The proposed first result is modest: the installed original ARM64 SIMH runs a disposable UNIX V7 copy, an independent operator uses its own Screen console, and an authenticated browser uses DC11 line 0. It does not use the panel daemon, alter boot selections, enable autostart or establish physical-panel acceptance.

## 1. Prepare a reviewable server on the Mac

**Proposed Mac work, not implemented in M5.1:** add an explicit terminal-only pilot entry point using the existing Go bridge, access gate and embedded assets. Keep `cmd/terminal-lab` and its isolation guards intact. Configure a fixed HTTPS origin/listen address, private credential/certificate paths and a finite endpoint allowlist. The browser must not choose network addresses, start/stop processes, access disks, attach Screen, or send panel/RPC commands.

Before seeking pilot approval, run the relevant Go race/authentication/bridge tests, frontend tests, all three browser engines and isolated genuine guest regression for that new entry point. Produce a static Linux ARM64 binary, its exact source revision/hash, a nonsecret configuration manifest and a reviewed certificate plan. Distinguish the new candidate from `checkpoint/m5.0`; do not replace an accepted tag.

**Stop condition:** missing reviewed binary, failed tests, unspecified credentials/origin, or any remaining lab-guard bypass. The read-only assessment is not permission to implement or install this entry point automatically.

## 2. Approve the exact changes and check readiness

The initial requested Pi scope should be limited to:

- One new owner-private pilot directory outside `/opt/pidp11`, with a versioned companion binary, private configuration/certificates, logs/measurements and a disposable guest disk.
- One manually started, separately named Screen session running the existing original simulator binary against that disk.
- One raw guest listener on Pi loopback port **40100**, and a terminal-only HTTPS listener on Pi loopback port **8445**, subject to a fresh conflict check.
- One explicitly authorized SSH local forward to the HTTPS listener, bound to Mac loopback.
- Controlled browser connection, keyboard arbitration, disconnect and bridge-stop tests, followed by an operator-led guest shutdown.

No service creation, boot-selection edit, original-image write, LAN listener, GPIO/panel action or firmware/network change belongs to this scope. Any later extension needs its own review.

Immediately before an approved run, confirm the intended power supply/cable, acceptable temperature and throttling state, free space and an independent SSH recovery session. Recheck process/listener state: M5.1's stopped/unused snapshot can become stale. If another emulator or maintenance session is active, stop the pilot procedure and coordinate; do not kill it or force a Screen detach.

The kit is unassembled. Do not start the scanner/panel daemon as a readiness check. The first pilot is deliberately standalone; assembly and physical-control testing are separate prerequisites for the later panel stage.

## 3. Preserve originals and create the disposable media

**Proposed Pi shell actions after approval:** choose one new private directory, for example `$HOME/pidp11-webdesktop-pilot`, and set a task-specific variable such as `PIDP_PILOT` to its absolute path. Refuse an existing destination. Do not repurpose shell system variables or make a path under `/opt/pidp11/systems` for this first test.

1. Record source revision and hashes of the original runtime binaries, launcher/control/helpers, selection file, and relevant UNIX V7 configuration files. Preserve read-only copies of those small files and their modes in the private evidence area. Confirm the existing verified golden backup remains available; this assessment did not reverify or rewrite it.
2. Verify the installed V7 guest image is not in use and will remain inactive during copying. If exclusive inactivity cannot be established, stop. A hash or copy of a changing disk is not a consistent backup.
3. Record a full source-disk hash, make an independent archived base copy, verify its hash, and protect that base against accidental writes. Then make a separate writable `guest/disk0.hp` for the pilot. Do not use a hard link, a symlink to the original, or mount the original filesystem.
4. Verify the original, archived base and initial working copy match before boot. Record their resolved paths, sizes and inode identities. Keep all three outside any web static-asset path. Reserve space for the base, working disk, an after-run archive and logs; approximately 1 GiB is a conservative minimum for this small V7 exercise, not a guarantee for other guests.

**Stop condition:** active or uncertain source disk, hash mismatch, wrong resolved path, insufficient space, or missing verified rollback evidence. No simulator attach should occur before these checks pass: SIMH may create an empty image when a target is missing.

## 4. Review the standalone guest configuration

Use a new `unix7-pilot.ini` in the pilot directory. The proposed contents are below. This is a **SIMH command file**, not a shell script. It has not been executed on the Pi. The process must start with the private pilot directory as its working directory, and `guest/disk0.hp` must already be the verified writable copy.

```text
; Proposed standalone pilot only. No original disk, GPIO or REALCONS connection.
detach all
reset all
set cpu 11/70 1M
set cpu idle
set rp0 rp06
attach rp0 guest/disk0.hp
set dci enabled
set dci lines=8
attach dci line=0,127.0.0.1:40100;notelnet
boot rp0
```

The eight-line setting preserves the installed configuration. Only line 0 receives a listener; lines 1–3 remain available for future approved conventional/physical assignments. The guest's inspected login files already enable tty00–tty03, so no guest-level edit is planned initially. If a login does not appear, investigate the copy's actual kernel/driver/getty behavior; do not edit the installed disk or casually enable every line.

Do not `do` the installed original boot file as a shortcut. It includes its own detach/reset/boot sequence and, in the ordinary variant, a REALCONS connection. Do not copy the M5.0 container-specific disk path or assume its four-line setting is required.

A proposed private Go endpoint file contains only:

```json
[
  {
    "id": "unix7-dc0",
    "label": "UNIX V7 pilot · DC11 tty00",
    "address": "127.0.0.1:40100",
    "kind": "raw-guest-line"
  }
]
```

The server entry point must validate this configuration, enforce private-file permissions and expose only the ID/label to the browser. The label is not proof of endpoint identity; the operator must verify the simulator instance and configuration that own the listener.

## 5. Start the approved guest with an independent console

**Proposed Pi shell action after approval:** manually start the original `/opt/pidp11/bin/client11` with the new command file inside a uniquely named Screen session such as `pidp11-terminal-pilot`. Use the pilot working directory and an explicit configuration path. Record the simulator and Screen process identities.

Do not call `pdp11control`, `pidp11.sh`, the switch scanner or the generic console helper. Their normal workflow targets the original session and physical daemon; broad stop operations can interfere with a separate test. Do not start the original launcher concurrently during the first pilot.

**Guest-console actions:** at the real boot loader, enter `boot`, then `hp(0,0)unix`. When the expected single-user shell appears, enter multiuser mode with Ctrl-D. These are the installed configuration's documented V7 boot steps and were demonstrated in M5.0, but remain unexecuted on this Pi in M5.1. Follow the actual prompts; stop on an unexpected state.

Verify the operator console works before starting the bridge. Confirm that the sole new terminal listener is loopback-bound and belongs to this simulator. Verify no new panel daemon/RPC registration or LAN guest listener appeared. Do not query panel inputs as a substitute for this check.

## 6. Connect the optional bridge and browser

Start the approved terminal-only candidate manually with its reviewed private files. It must attach only to the identified DC11 listener and serve embedded assets over loopback HTTPS. It should run without root or access to GPIO. In an owner-local first pilot, it shares the trusted owner's account privileges; that is not final least-privilege separation. A later service should use a dedicated account and separate permissions.

The proposed Mac SSH forward is:

```sh
# Mac shell, only after the pilot is explicitly approved.
ssh -N -T -L 127.0.0.1:8445:127.0.0.1:8445 pidp11
```

Use the existing SSH configuration and host keys. This tunnel is not created during M5.1. If either local port is occupied, stop and review the origin/listener configuration; do not kill an unknown process or change ports without updating exact-origin and certificate checks.

Use `https://127.0.0.1:8445` only with the specifically approved certificate/trust arrangement. Never disable certificate checking globally or reuse demonstration credentials. Keep guest logins and browser credentials separate. No account password or token belongs in a command URL, screenshot or public log.

The browser must connect read-only, acquire its keyboard explicitly and select the guest-appropriate erase mapping. UNIX V7's inspected base uses `#` for character erase; verify the pilot guest's actual terminal settings. Start with a harmless directory listing and a unique echo marker. Keep the operator Screen console accessible throughout.

## 7. Validate independence and bounded behavior

Record actual observations, timestamps, selected nonsecret transcripts and process-level memory/CPU samples. Use modest commands, not a stress test. Stop if temperature/throttling/power behavior becomes unacceptable or if the original routes are disturbed.

| Test | Required observation |
|---|---|
| Real command | Browser output includes the guest's result, not merely echoed input or a fixture |
| Two viewers | Both see output; only the explicit owner can type |
| Competing acquire | Current writer is not displaced |
| Browser close / refresh | Guest and operator console remain usable; reconnection does not acquire automatically |
| Lease expiry / network interruption | Keyboard authority expires without injected characters or replay; no CPU-stop claim |
| Bridge stop | Browser line disconnects, but guest and independent console continue; record any guest hangup/session loss |
| Bridge restart | Fresh authentication/connection/acquisition required; no stale command replay or silent guest switch |
| Screen independence | Human operator can use the explicitly named pilot session without browser takeover; do not force-detach another operator |
| Resources | Bridge RSS/CPU recorded separately from simulator/browser; compare with targets without declaring a short run a soak |
| Network boundary | Guest and HTTPS sockets remain loopback-only; no new LAN listener or panel RPC interaction |

Guest keyboard handoff can leave already delivered partial input in the guest's terminal buffer. Operators must clear or inspect that state deliberately; no automatic erase/Return is permitted. A bridge crash can lose a login or application on that line. The success condition is simulator/operator independence, not survival of every guest foreground task.

A first pass may use two short idle/active samples and a few reconnects. A later approved sustained workload must establish Pi performance, thermal behavior and tail latency; M5.1 does not authorize it. Preserve failed results and uncertain delivery states.

## 8. Shut down and roll back without losing work

1. Release browser ownership and stop only the pilot bridge. Preserve any guest work through the guest before shutdown. Do not use broad process-name kills or the ordinary launcher stop command.
2. In the pilot's independent **UNIX V7 console**, reach a known shell prompt and run `sync` three times, as documented by the installed profile. Then use that simulator's operator stop mechanism and `quit` from its monitor. This is a planned V7 procedure, not a universal crash-recovery guarantee. If the console/guest state is unknown, stop the procedure, retain the disk and seek operator recovery rather than deleting it or claiming clean shutdown.
3. Verify the identified pilot simulator/bridge and loopback listeners have exited. Close only the pilot Screen session and SSH forward. No power cycle is part of rollback.
4. Recheck original configuration/runtime hashes and the original inactive V7 image hash. They must match the pre-pilot manifest. If they differ, preserve evidence and investigate; do not overwrite a changed original automatically with an old backup.
5. Archive the pilot's post-run working disk and logs separately from its read-only base. Retain them until the owner decides what to keep. Uninstall the companion binary/configuration only after required guest data is retained; revoke pilot credentials and remove any explicitly added trust exception according to the approved certificate plan.

Because this first pilot adds no service, selector entry, firewall rule or original-file edit, rollback requires no restoration of those settings. A later optional service must have a reviewed uninstall manifest: stop/disable only its own unit, remove only its own program/configuration, explicitly preserve guest media, and reverse only the documented added network/trust rules. Do not uninstall existing rpcbind, Screen, SSH or simulator dependencies.

## 9. Separately approve original-launcher and physical coexistence

After the standalone terminal pilot succeeds and hardware is ready, review a separate original-path test. One candidate is a new opt-in guest profile directory with copied media and a new unused boot-selection entry. The unchanged launcher would then follow its normal selected-profile, Screen, panel-daemon and REALCONS path. Preserve all existing selections and defaults. The precise selector value and complete diff must be reviewed before modification.

That test must establish, with the owner present, that physical switches, lamps, operator console and guest access behave as expected before and after the companion starts/stops. It must also verify guest switching does not silently attach a browser to the wrong OS or line. No extra panel RPC reader/server, remote panel authority or distribution switcher belongs to this terminal-only work.

Until that separate test passes, state the result accurately: **standalone installed-binary terminal compatibility demonstrated**, not “physical PiDP-11 coexistence proven.” M4's remote-panel safety blockers remain outside both terminal stages.
