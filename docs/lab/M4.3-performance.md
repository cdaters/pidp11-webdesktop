# M4.3 resource and stability measurements

2026-11-17. **Mac Apple M4 Pro / OrbStack Linux ARM64 and Mac Chromium, not Raspberry Pi measurements.** CPU percentages use one core = 100%. The original Pi 3B+ budgets remain targets in [roadmap](../roadmap.md), not acceptance claims. Raw evidence and hashes are in [m43](m43/).

## Primary observation workload

1,801.44 seconds with original REALCONS plus the optional passive publisher, a RAM-only running INC/branch loop, continuous changing snapshots, eight TLS1.3/WSS viewers, one 30-second reconnecting viewer, one deliberately slow reader, session renewal/expiry, and a 60-second HALT phase every five minutes. All activity stayed inside a read-only, network-none container with bounded tmpfs, 512 MiB memory and two CPU allocation limit. The browser workload below ran concurrently for part of this test, as did bounded development/regression work; these are stability/resource observations, not a quiet-host microbenchmark.

The primary harness inherited RSS from `/proc/PID/stat` and PSS from `smaps_rollup`. The kernel resident counter is approximate and can undercount; therefore these separately sourced values can misleadingly show PSS above RSS. Do not interpret that as memory physics or subtract them to calculate sharing. The final harness now reads **both Rss and Pss from smaps_rollup**. A separate 60.09-second final confirmation passed with 13.01 MiB RSS peak / 13.00 MiB PSS peak and 0.433% observer CPU. That confirmation does not replace the long-run record or imply a second 30-minute final-revision soak. The kernel documentation recommends smaps/rollup for accurate resident accounting: [proc memory counter limitations](https://man7.org/linux/man-pages/man5/proc_pid_statm.5.html).

No sustained memory growth was visible in the long observation sample; startup/GC/reclamation and approximate RSS accounting explain why a peak is more useful than an extrapolated leak rate. This does not establish unlimited runtime stability.

### Slow-reader finding

The deliberately slow Go client consumed one message every 150 ms while the server published up to 20 Hz. It received 11,868 frames, only two fresh, and eventually read a frame **1,044,119 ms old**. Service memory remained bounded, but transport buffers retained history. A 500 ms server write deadline cannot guarantee that an application reads a recently sent frame. The frontend now rejects stale freshness claims, marks age explicitly and reconnects when an allegedly-fresh stream is over one second behind. A browser regression proves it discards that stale stream, reconnects passively and displays simultaneous physical controls. The intentionally slow probe does not implement that frontend recovery; its record preserves the discovered failure mode rather than hiding it.

## Browser workload

See the recorded browser figures appended below and the [retention investigation](M4.3-browser-memory.md), including the failed initial DOM budget and native undo-history evidence. The complementary workload uses four independent mock terminals, HELP/ANSI bursts, arrow-key filtering, one idle minute per five-minute phase, terminal destruction/recreation, bounded mount/eject operations and sustained SVG updates. Browser input timing includes automation and two animation frames; it is not a guest terminal round-trip or LAN acknowledgment. Browser JavaScript heap is not browser-process RSS/PSS. The raw field named `renderer_cpu_percent` is specifically CDP `TaskDuration` change divided by wall time: a main-thread task-time ratio, not whole-browser process CPU. CPU across all browser/GPU processes is not measured by that field. The browser is on the user's Mac, not part of the Pi's 1 GiB service budget.

The final incremental source changes—credential-file validation, stalled-login lock isolation, stale-stream recovery, simultaneous observed controls, native-button activation and cosmetic label/highlight/device refinements—have focused/full regression coverage after the primary observation workload began. They were not all present for that entire observation soak. The final timed browser run uses the final embedded frontend assets and ran after the primary observer workload; it is not a simultaneous end-to-end rendering test of REALCONS. Its inherited raw scope label is corrected explicitly in the archived metadata, without altering measurements. The SVG definition count and per-switch update architecture remained the same. This scope is recorded in metadata rather than relabeling the runs as testing every final line for 30 minutes.

## Broker, allocations and emulator impact

The final M4.1 regression's five-second idle broker sample used **1.999%** of one core; its 15-second, two-viewer/300-command sample used **3.133%**, with **1.488 ms p95** command acknowledgment including driver IPC. A preceding repetition was lower, demonstrating sensitivity to host load and short windows. The earlier ~2.4% idle concern remains open against the <1% target. The observer avoids mandatory mediation entirely; changing the language or reducing safety polling is not a measured solution.

Mac Go allocation benchmarks, three repetitions:

| Path | Representative result | Implication |
|---|---|---|
| Physical read with existing reused receive buffer | 28–29 µs; 12,274 B/op; 151 allocs/op | About 0.59 MiB/s at 50 Hz in this local benchmark; substantial residual allocations remain |
| Prior receive allocation comparison | 32–33 µs; about 77,864 B/op; 152 allocs/op | Reuse already avoids roughly 64 KiB per call; this is not a new M4.3 optimization claim |
| Snapshot JSON | 2.7 µs; 4,218 B/op; 71 allocs/op | Eight viewers at 20 Hz imply roughly 0.64 MiB/s of this measured allocation path, not total process allocation |
| Simulated poll | about 18 ns; 0 B/op | No reason to replace the mock hot path |
| Mock command round-trip | 35–37 µs; about 6,370 B/op | Local microbenchmark, not emulator dispatch or LAN latency |

The longer instruction benchmark performs seven alternating **one-billion-instruction** samples per binary after a 100-million warmup:

| Variant | Median process CPU seconds | Change versus original |
|---|---:|---:|
| Original | 5.89 | baseline |
| Fence copy, disabled | 6.12 | +3.90% |
| Publisher copy, disabled | 6.01 | +2.04% |

Median wall changes were +4.02% and +1.92%. The short ordered 100-million-instruction comparison gave a misleadingly large improvement; it is retained as raw evidence but not used to close the overhead concern. The <3% emulator-impact target remains open, especially for the fence copy. The enabled publisher's guest-throughput impact is not isolated by this microbenchmark. These runs use no guest OS, physical GPIO, target Pi thermals or production storage.

## Recovery and deployment targets

The optional UDP budget copy measured 219 ms silent registry failure, 2,014 ms aggregate descriptor exhaustion, 330 ms confirmed quiescence after lost GET/broker crash, and 348 ms watchdog acknowledgment after a held lamp-test callback in an already stopped/armed consumer. These are finite observations, not guaranteed deadlines. The [recovery report](M4.3-recovery.md) separates authorization, dispatch, completion, running state and confirmed quiescence.

Retain the Pi targets: ≤24 MiB idle RSS, ≤48 MiB active / ≤64 MiB peak, <1% idle / <5% active mean CPU, <3% emulator throughput impact, <100 ms p95 panel freshness/acknowledgment, and <40 KiB/s per panel viewer. Production acceptance must measure on the authorized Pi with its actual GPIO load, guest workload, clocks, thermals and conventional access. Go remains justified; no measured language comparison supports a Rust migration.

## Deployment artifacts

The stripped, statically linked Linux ARM64 mock executable is **6,488,226 bytes (6.19 MiB)**. Embedded browser assets total **426,470 bytes**, or **114,107 bytes (111.43 KiB)** when gzip sizes are summed per file. This includes the existing lazily loaded xterm renderer and its CSS/FitAddon; no new runtime dependency was added. The self-contained offline HTML is **436,605 bytes**. Build-specific CSP nonces make hashes vary when packaging is rerun; the exact artifact hash and per-file sizes are recorded in `m43/metadata.json`. The ordinary executable's Go dependency graph has no laboratory RPC, consumer-fence or observation package.
