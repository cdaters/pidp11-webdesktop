# M5.5 supervised physical pilot — findings and stopped recovery

**2026-11-19 · Actual Raspberry Pi 3B+ and assembled PiDP-11/70. Overall acceptance is blocked.** The original launcher successfully booted the copied UNIX V7 pilot. Genuine browser terminals, the independent Screen console and owner-operated physical controls worked together. However, the subsequent attempt to select diskless IDLED started RSX-11M-PLUS instead, despite the owner's visual confirmation that all 22 switch-register paddles were down. That failed fallback prevents an accepted physical-coexistence checkpoint. No acceptance tag was created.

The [Mac preparation report](M5.5.md) remains the record of the isolated tests. This report covers the separately authorized execution of the [supervised procedure](M5.5-pilot-plan.md), including the unexpected guest, explicit recovery authorization and rollback. No production service, autostart, remote panel control, GPIO change, firmware change or power/network reconfiguration was introduced.

Original launcher, simulator, panel-daemon, scanner and reviewed configuration hashes matched the retained baseline. The original source revision was `26d20beda0c6b5a1d3a5cb3d7a4dd494e02bff75`. A complete inventory recorded 609 regular files and the installation's symbolic links before changes. The retained compressed golden backup matched its checksum, and the earlier source-card/image digest records agreed; no new restore rehearsal was performed.

The tested application was the same static ARM64 binary as Mac acceptance, SHA-256 `69b609ea7b41f24c61daaeb1a6fa2292782ebc72ead3cf9ccdf53f699598f443`, from the source described at implementation checkpoint `32e5fc4` and preparation documentation checkpoint `11a24af`. Application, simulator and panel-control source were not changed during this pilot.

The only installed additions were the separate `unix7-web-pilot` profile and its independently writable V7 disk, the approved `0017` selection row, and private owner-local bridge/evidence files. The original V7 disk was copied first to a protected base, then to a distinct writable file; complete hashes and file identities were checked. The candidate retained all original REALCONS settings, including the 1 ms interval. Its sole boot-file difference was the dedicated loopback DC11 listener described in the preparation report. Original guest profiles and binaries were not replaced.

## Successful V7 coexistence checks

The first physical selection attempt reached IDLED. The owner then clarified that only SR0–SR2 were up and SR3–SR21 were down. That is consistent with an unmapped selection falling back to IDLED, but the scanner's raw value was not captured. The diskless session exited through the SIMH monitor. Only after the owner explicitly confirmed SR0–SR3 up, all remaining SR switches down and HALT at ENABLE did the coordinator retry the original launcher **without a selection argument**.

That launch selected `unix7-web-pilot`. Process/file evidence identified the original simulator, the copied pilot disk, the original panel daemon and a loopback-only terminal listener. V7 booted through the normal Screen console. A root-directory listing and fresh echo challenge established conventional console access before the browser connected.

The owner then operated HALT and CONT. RUN was lit before HALT and dark while halted; the formerly flashing lamps became steady. Screen independently reported `Simulation stopped`. The owner returned HALT to ENABLE and explicitly confirmed pressing CONT. RUN lit and address/data activity resumed, and a fresh V7 console echo succeeded. These are separate owner observations and software observations, not inferred physical lamp states.

The manual bridge used fresh private credentials, a temporary loopback TLS certificate and an owner-controlled SSH tunnel. Certificate validation used that exact certificate before isolated browser contexts were opened; no global trust settings changed. Chromium, Firefox and WebKit each passed genuine V7 command/echo, erase-key, three-viewer, observer, conflicting-writer, disconnect/reconnect and refresh checks. Reconnection began read-only and did not replay display history or retain keyboard ownership. The independent Screen console answered fresh challenges after browser closure and during a bridge-only stop/restart. A new bridge required fresh authentication and explicit keyboard acquisition. This was a controlled restart against the same independently verified simulator, not automatic reconnection to another guest.

With a read-only browser observer connected, the owner confirmed that RUN remained lit and that rotating the DATA selector one position and back changed the lamps normally. After the actual bridge and tunnel were stopped, a new Screen echo succeeded and the owner repeated the same physical observation. The browser grants no physical-panel authority; its SVG panel remained simulated throughout.

V7 then completed three `sync` commands through Screen. The operator interrupted into the SIMH monitor and issued `quit`; `Goodbye`, Screen exit and original daemon cleanup were captured. The stopped working disk and a separate verified read-only after-run copy were preserved privately.

## Failed IDLED fallback and bounded recovery

After that clean V7 exit, the owner confirmed selection `0000`. The original no-argument launcher instead generated an **RSX-11M-PLUS** boot command. Its console showed the original RSX disk being attached and guest startup reaching the time/date question. The browser bridge had already been stopped and was not restarted; no browser could attach to this unexpected guest.

The coordinator stopped the test sequence and used a single Screen Ctrl-E to pause the simulator. No RSX console command, reboot, launcher retry or disk restoration followed. The owner explicitly reconfirmed that **all 22 physical SR paddles were down**. The report does not replace that observation with an assumption that a switch was left up.

A read-only comparison while paused found the RSX disk's on-disk SHA-256 and modification time equal to the pre-pilot baseline. Because the simulator still had the disk open, this was treated as provisional. The owner then expressly authorized SIMH `quit` **without resuming RSX**, followed by immediate hash and metadata verification, and authorized safe rollback only if the disk remained unchanged.

SIMH printed `Goodbye` and the original launcher and daemon exited. The closed RSX disk matched its baseline exactly in SHA-256, modification time, size, mode, owner/group, inode and device. No restoration, overwrite or repair was needed or attempted. This is an unchanged-media result after a controlled simulator exit; it is not a claim that a normal RSX guest shutdown was performed.

**The selection discrepancy remains unexplained.** The resulting profile is known, but the scanner's raw numeric output was not logged. No extra scanner execution, GPIO diagnostic, RPC input poll or further launcher start was used to investigate. The approved map edit added only `0017`; it did not change the existing IDLED or RSX mappings. Neither operator error, hardware failure nor a scanner/software timing defect has been established.

The next investigation must separate selection diagnosis from guest execution. Review the retained launcher/scanner source and evidence on the Mac first, then prepare an explicitly authorized diagnostic that cannot boot an original writable guest. Do not repeatedly launch against the normal guest library to reproduce the discrepancy. Do not pin an explicit IDLED argument and present that as a successful physical-selection test.

## Operator evidence and test limits

Two private capture checks needed correction. Batched initial console commands placed a shell prompt before the echo response; the original saved output was validated separately from the echoed input without resending a command. Later, Screen acknowledged a hardcopy command before its file write completed, so the third shutdown-sync capture initially read as empty. Shutdown paused before any interrupt; a later read of that same file verified all three completion prompts. The private helper was changed to wait for a nonempty capture. Original failed captures remain preserved. These were operator-evidence issues, not application fixes or substitute guest results.

The original panel daemon also emitted a real-time-priority warning. No privilege or scheduling changes were made, and no scheduling guarantee is inferred from the functional checks.

The actual Pi run did not repeat the Mac lab's RPC crash tests, listener-detach/replacement experiment, remote-control experiments or broad desktop suite. No native Safari, physical serial expansion, unattended guest switching or LAN service was tested. Same-process guest changes can still be invisible to the bridge; the actual bridge must be stopped before intentional guest changes.

## Rollback and final disposition

After closed-disk verification, the coordinator removed only the exact approved appended map row, restoring original bytes and recorded file metadata. The inactive copied profile was moved out of the installation into the private pilot archive; its working disk and independently verified after-run copy were retained. Temporary writer/observer tokens and the TLS private key were removed from the Pi and Mac. No permanent service had been installed.

The final comparison found **all 609 original regular files and all three symbolic links unchanged**. File comparisons covered SHA-256, size, mode, owner/group, modification time, inode and device; the original Git status also matched. `pdp11control stat` reported down, Screen reported no sessions, and no simulator, panel daemon, bridge or pilot listener remained. The Pi stayed powered on in its normal stopped state. No further guest was started.

Final integrity and stopped-state results are recorded in [physical validation](m55/physical-validation.json), alongside [browser results](m55/physical-browser-acceptance.json), [resource samples](m55/physical-measurements.json) and the [private-evidence index](m55/physical-evidence-index.json). Full maps, addresses, credentials, raw console captures, screenshots and guest disks are not published.

The V7 coexistence subtests passed. The required physical-only IDLED fallback did not, and the active CPU target was not met in the short sample. **There is no accepted M5.5 physical checkpoint and no production-integration approval.** The machine is to remain in its normal stopped state while the selection discrepancy is investigated; no further guest start is part of this recovery.
