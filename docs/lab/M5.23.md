## Genuine disk result

A fresh working copy of the legitimate retained **RT-11SJ (S) V05.03** image booted
on an original 11/70, 4 MiB configuration with `RL0` explicitly set to RL02. Original
console `SHOW CONFIG` identified boot from `DL0:RT11SJ`; `SHOW DEVICES` reported
resident DL. `DIR *.SYS` returned 63 files/985 blocks, including the actual installed
monitor and handler files. Later `DIR DL:DL.SYS` returned one four-block file.
These are genuine guest filesystem reads, independent of the browser.

At an independently verified idle monitor, the private harness paused the CPU,
recorded `SHOW RL`, `SHOW RL0` and named RLCS/RLDA/RLBA/RLMP variables, then hashed
the quiescent working file. Capture showed RL11, RL0 attached, RL02/write enabled,
RLCS octal `000315`, RLDA `000050`, RLBA `005772`, RLMP `000000`.
Logical geometry: 512 cylinders, two heads, 40 sectors/track, 256 bytes/sector;
**10,485,760 bytes capacity**, distinct from **10,478,080 stored image bytes**.

Both the untouched base and captured working copy had SHA-256
`543277ee81fb4c024d19242bf6d6a04c81a257c48fe4cece256a42de3fe8dd98`.
The collector opened only the allowlisted file with read permissions and verified
its identity/hash/length before publishing captured metadata. The original console
was resumed after capture and remained usable. No continuous block-read/write
activity was observed or inferred. [Captured disk facts](../../lab/m523/results/disk-capture.json).

## Genuine tape result and guest boundary

A separate original simulator process, within the same isolated container, ran a
small authored PDP-11 program against **TM11/TU10, TM0**. The authored SIMH tape
contained one **42-byte** ASCII record followed by two filemarks, **58 bytes total**.
It was attached read-only and write locked. SHA-256:
`a2b62e0ade533d3a20037755c75ba410bfddc128184b9a83298cfa9e7698c777`.

Actual CPU instructions set the TM byte count/address, issued read commands, waited
for completion and halted. Independently examined DMA memory matched all 42 authored
bytes. No payload was obtained by pretending a host-file read was guest DMA.

| Stage | Logical image POS | MTS (octal) | MTC (octal) | Meaning |
|---|---:|---|---|---|
| Attached | 0 | `000145` | `000200` | Online, protected, beginning of tape |
| Data record read | 50 | `000105` | `000202` | Exact DMA payload, count exhausted |
| First filemark | 54 | `040105` | `100202` | EOF/filemark, error summary expected |
| Second filemark | 58 | `040105` | `100202` | Second EOF/filemark |
| Read beyond image | 58 | `000505` | `100202` | Original end-of-medium mapping to bad-tape/error status |

The final snapshot accurately shows an observed error summary and end-of-medium;
it does not label the device idle, make the reels spin or convert byte offsets into
feet. Capacity-based EOT was not qualified. The intermediate filemark evidence is
preserved separately from the final capture. [Stages](../../lab/m523/results/tape.json),
[final snapshot](../../lab/m523/results/tape-capture.json).

RT-11 inventory found MT/MS/MM handler files but reported them not installed. That
is an available starting point, not proof of a working guest tape utility. No matched
label/record/utility sequence was qualified in M5.23. The precise remaining step is
to verify a supported historical tape workflow and install/use its matching handler
on a fresh disposable guest. No driver was declared missing; no guessed guest tape
command was run to manufacture success. Tape evidence here is explicitly CPU/device.
