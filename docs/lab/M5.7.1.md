## Interpretation and next hardware inspection

The observed decoded value did not respond to the owner-confirmed movement. That supports investigating a persistently asserted SR0 signal path. It does not prove that the switch contacts failed to move, identify a solder fault, measure a voltage or rule out intermittent behavior between captures.

The pinned original C scanner maps row 0 to GPIO16 and column 0 to GPIO26, setting SR0 when that column read returns low. These are **BCM GPIO numbers, not header pin numbers**. The [M5.7 source analysis](M5.7.md#what-the-evidence-narrows-down) records the source revision, polarity, requested 10 µs row delay, process-status convention and unchanged map resolution. The same raw 1 predicts `0001` → `rsx11mp`; no guest was launched to confirm that prediction again. Neither number formatting nor browser-terminal behavior explains the raw asserted bit.

A contact held closed, solder bridge, connection/assembly problem, or electrical/initialization issue could produce this observation. No single one is established. A simple global inversion of all switch bits does not explain why only SR0 remains asserted. No software workaround or forced boot selection is proposed.

The justified next step is **owner-reviewed, separately authorized inspection**, not execution of the following procedure now:

1. First verify the SR0 label and paddle travel visually against a neighboring switch, without pressing other controls. Record clear front/rear photographs and the PCB revision before deciding on disassembly. A paddle position is not a continuity measurement.
2. Before opening, touching connections or using continuity/resistance mode, arrange an authorized normal Linux shutdown, disconnect all power sources, and confirm the assembly is unpowered. No shutdown or power change occurred in M5.7.1. Do not probe resistance on a powered board or move/reseat GPIO connections live.
3. Use the assembly guide and schematic matching that PCB revision to identify the SR0 contact and its row/column connections. Inspect orientation, full travel, connector seating, nearby joints and possible bridges. Do not assume a physical connector pin from the GPIO number or from a different board revision.
4. If the owner is comfortable with the instrument and the matching schematic is available, compare the unpowered SR0 contact's open/closed behavior in both positions with a known neighboring switch. Record the points tested and meter readings. Stop if access, pin identity or the expected contact behavior is uncertain; seek the kit maintainer's guidance rather than guessing or soldering speculatively.
5. Propose any repair from the actual inspection evidence. Reassembly, power-on and another bounded scanner comparison require separate approval. Do not start a guest merely to check a repair.

No repair, continuity test, live voltage probing or further movement was performed. The current all-DOWN position was left unchanged.

## Memory-limit finding and implemented strategy

Fresh read-only inspection confirmed the Pi still exposes `cpuset cpu io pids`, without `memory`, and retains `cgroup_disable=memory`. `DefaultMemoryAccounting=yes` does not supply the missing controller. This milestone did not test service startup or allocation pressure on the Pi and changed no Pi service or boot setting.

`MemoryMax` depends on the kernel memory controller; a configured systemd property alone is insufficient. Swap has its own limit. The candidate retains the 96 MiB boundary and adds `MemorySwapMax=0`. See [systemd 257 resource controls](https://www.freedesktop.org/software/systemd/man/257/systemd.resource-control.html).

The packaged unit now invokes `serve -require-memory-limit`. Before reading private configuration or opening any socket, the command checks that `/sys/fs/cgroup` is the kernel's unified cgroup filesystem, locates its own membership, and requires readable memory accounting, a positive local `memory.max` no greater than 100663296 bytes, and `memory.swap.max=0`. Missing, unlimited, oversized, malformed or unreadable records cause a clear error and process exit. Unsupported cgroup layouts also fail closed. The check writes nothing and does not alter controllers. `Restart=no` remains, preventing a failed-start retry loop.

The original physical machine is the fallback: **no automatically weakened companion mode** is offered. Direct development invocations without that flag remain available for the existing disposable lab; they are not equivalent to the protected installed unit. The file-only `check` subcommand still checks configuration rather than service containment. This startup check cannot prevent an administrator later changing limits or membership; inspect effective settings again during an authorized deployment. It does not guarantee survival of machine-wide memory exhaustion.

The unit also sets `GOMEMLIMIT=72MiB`, a Go-runtime target leaving nominal room beneath the kernel ceiling. It is not an RSS cap and cannot constrain all process/kernel allocations. A live heap larger than the target can exceed it; increased collection can also cost CPU. See the [Go garbage-collector guide](https://go.dev/doc/gc-guide#Memory_limit). The existing 24/48/64 MiB RSS targets and CPU targets remain unchanged; representative Pi measurements are still required.

## Disposable ARM64 Linux results

The isolated Debian Trixie environment used systemd 257.13 with its external interface down, no shared host-home directory, no SSH agent forwarding and no guest media/GPIO. Its outer 1 GiB laboratory limit stayed in place. The missing-controller case disabled memory control in a **test parent slice**; it modeled missing local enforcement without changing a kernel boot flag. It is not a reproduction of the Pi's entire kernel configuration.

| Case actually tested | Observation |
|---|---|
| Protected unit, 96 MiB and zero swap | Started detached; actual kernel files matched; HTTPS passed certificate verification; hardening properties rechecked |
| Parent disables local memory controller | Refused before a listener; systemd still reported configured `MemoryMax=100663296`, demonstrating why that property alone is insufficient |
| Unlimited or 128 MiB local limit; unlimited swap | Each refused before a listener, status 1, no restart |
| Restored protection | Manual startup worked again |
| Go soft target 72 MiB, 112 MiB retained heap under a 256 MiB outer test limit | Allocation completed above the soft target |
| `LimitRSS=96M`, 112 MiB retained heap | Allocation still completed; this is not a working Linux memory boundary |
| `LimitAS=96M` | Go failed to reserve its startup address space; unsuitable as a substitute RSS limit |
| Separate bounded 128 MiB allocation attempt under 96 MiB kernel limit and zero swap | Fixture was killed with `Result=oom-kill`, signal 9; independent sentinel remained alive |

The [machine-readable lab results](m571/memory-lab.json) retain actual byte counts and effective properties. The allocation fixture is a separate test program, not an induced OOM in the desktop or a guest. Kernel limits may briefly overshoot under some conditions and can invoke the in-group OOM killer; they are not a promise of zero transient excess. [Kernel cgroup documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory) describes that boundary. `LimitRSS` is ineffective on Linux and `LimitAS` restricts address space rather than resident memory, consistent with the [systemd execution manual](https://www.freedesktop.org/software/systemd/man/257/systemd.exec.html#Process%20Properties).

An RSS polling watchdog was considered but not substituted for kernel containment: it can miss an allocation burst, fail itself, and cannot prevent host pressure before the next poll. Lower viewer/output bounds remain useful but cannot prove total process memory containment. No new watchdog daemon was added.

The unchanged synthetic-peer [service lifecycle checks](m571/systemd-lifecycle.json) passed authentication, wrong-origin rejection, EOF retirement, restart/session revocation, no automatic redial, crash/restart detachment and independent-peer survival with the new unit. Their evidence is in [Chromium](m571/detached-chromium.json), [Firefox](m571/detached-firefox.json) and [WebKit](m571/detached-webkit.json).
