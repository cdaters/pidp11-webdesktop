## ARM64 startup investigation

The preserved M5.13 runtime has SHA-256
`ce3d7c9dbf4396931847a7da4a21f7b4d0fa00b3bb30e9b02018cb5eccc46b21`.
`file` and ELF inspection identify a static, stripped AArch64 executable with no
interpreter segment. Executable permissions, load segments, memory mappings and
resource limits were inspected. Both isolated environments used ARM64 Linux
`7.2.12-orbstack-00394-gbecdd6130068`; they are two filesystem contexts under the
same virtualization platform, not independent kernel/physical-machine coverage.

| Controlled original-runtime comparison | Result |
|---|---|
| Linux copies to Mac FUSE-mounted work directory, immediate execution | 12/12 exit 0 |
| Mac-host copies to that mount, immediate Linux execution | 12/12 exit 0 |
| Native Linux overlay copies, immediate execution | 12/12 exit 0 |
| Native Linux VM btrfs provisioning | 12/12 exit 0 |
| Original runtime under `strace` | Exit 0; private syscall trace retained |
| Original runtime under `gdb` | Exited normally; no crash/backtrace obtained |
| Execution from the existing no-execute `/tmp` mount | `EACCES`, errno 13; protection preserved |

The 48 ordinary successful starts and two debugger runs do **not** demonstrate a
fix. Native Python return codes distinguish signal termination from a positive
exit status in these new tests. The original two records contained code 139 but
no native wait status, core dump or signal trace. The conventional interpretation
is 128 + SIGSEGV; the old record alone does not prove a signal rather than an
explicit status. The inspected core limit was zero, so no missing core is invented.
No OOM events were recorded in the bounded container comparison.

The first harness stopped at the no-execute mount before saving its complete
summary. The harness was corrected to record execution errors and persist each
case, then repeated into fresh directories. No mount protection was weakened.
The final candidate passed 24 mount/overlay starts; an earlier correction-only
candidate also passed 24, recorded separately. The aggregate provision medians
were about 4.84 ms for the original and 16.06 ms for the corrected runtime in this
small diagnostic workload. File syncing adds work, but these short samples do
not isolate its cost or establish a Pi performance regression.

[Sanitized startup results](../../lab/m514/results/arm64-startup.json) preserve
counts, executable hashes and exit distinctions. The source of the original
failure remains unknown. If it recurs, retain the exact executable and failed
private directory, native signal/exit status, mount/limit metadata and syscall or
core evidence before any retry. A different ARM64 kernel/filesystem platform is
a useful next comparison; repeated success on this one is insufficient.

## Reproduced defect and focused corrections

A separate real Linux `RLIMIT_FSIZE=100` experiment made the old runtime return 1
while leaving a truncated `config.json` in its new 0700 directory. Unordered map
iteration could write the configuration before its private dependencies. This
was a handled write failure, not a crash or memory-containment failure.

Provisioning now creates a fresh private directory, anchors access with Go's
`os.OpenRoot`, writes private files in a stable order and publishes `config.json`
last. Every file is exclusively created, synced and closed. On a handled failure,
it removes only names created by that call, verifies the directory identity and
removes it only if empty. Unknown files survive and cause a reported cleanup
failure. Existing configurations are never overwritten.

The final binary under the same file limit returned 1 with no partial files or
directory. Regression tests inject disk-full failures at each of the three writes,
including partial writes, and check retry, existing-data preservation and unknown
file retention. SIGKILL, power loss or failed cleanup may still leave an incomplete
directory; this is not a crash-atomic transaction.

Malformed JSON and origin diagnostics no longer echo arbitrary private input.
Missing private directories and occupied sockets identify the recovery boundary.
The service never automatically removes an existing socket. Tests include a secret
canary, directory ownership and preserved stale-socket identity. The
[troubleshooting guide](../getting-started/alpha-troubleshooting.md) explains
stopped recovery without broad deletion or protection bypasses.

## Lifecycle and containment evidence

The full Go suite retains process exit/replacement, concurrent attachment,
authorization expiry, keyboard leases, disconnects, epoch fencing and observer
replacement coverage. Four Linux process/socket cases and real ARM64 ownership
and provisioning tests passed in disposable Linux.

A genuine V7 session added a focused fault sequence:

1. An explicitly approved browser issued a genuine guest command.
2. Stopping the exact lab observer with SIGSTOP caused authority to expire and
   keyboard acquisition to become unavailable. Continuing it did not revive that
   authority; the expired connection was no longer accepted by the observer.
3. The independent console and traditional serial terminal continued to answer.
4. SIGKILL targeted only the owned companion. V7 still answered at its console.
5. Restart refused the stale private socket. After confirming the killed child
   was absent and the exact service-owned socket was stale, the harness removed
   only that socket. Explicit restart produced a new detached instance and
   rejected the old browser session.

[Supervision result](../../lab/m514/results/supervision.json). No automatic
emulator restart, guest switch, browser reconnection or keyboard transfer was
introduced. An OS change inside a surviving process/stream is still not detectable
from these identities; the operator must stop the actual bridge/observer before
intentional changes and independently approve the new guest.

The disposable Debian Trixie ARM64 VM was isolated from host files and external
network access during testing. The real preflight correctly refused its missing
Oscar installation; no dummy installation was manufactured. The package installed
stopped and disabled. Platform-wide systemd overrides were countered in this
one owned test unit so the **distributed protections were actually effective**:

- `MemoryMax=100663296` (96 MiB), `MemorySwapMax=0`;
- `NoNewPrivileges=yes`, `PrivateDevices=yes`;
- `ProtectSystem=strict`, `ProtectHome=yes`, `Restart=no`.

An idle snapshot measured **8,736 KiB RSS and six threads**. This is a short VM
sample, not physical Pi CPU, latency, emulator-impact or endurance qualification.
The existing Pi targets remain unchanged. SIGKILL produced no automatic restart;
explicit restart was detached and refused old approval. Stopped rollback to the
actual M5.13 runtime with a compatible configuration, then return to M5.14, passed.
With the memory controller deliberately withheld from only the disposable test
slice, startup refused before opening the HTTPS listener. Restoring the controller
restored protected detached startup. The service was then stopped, uninstalled,
and its dedicated account/private inputs removed before deleting the owned VM.
