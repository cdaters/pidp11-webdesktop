# Proposed original-launcher terminal coexistence pilot

**Owner review only; not executed or authorized by M5.4.** This proposal tests one copied UNIX V7 profile through Oscar's original launcher with the assembled physical panel and a manually started terminal bridge. No automatic service, remote panel control, passive publisher patch or other guest integration is included. The [design](M5.4.md) explains the evidence and identity limits.

The fallback is ordinary physical-switch selection, the original Screen console, the original emulator/panel daemon, and the original guest profiles with the Web Desktop absent. A failed checkpoint stops the experiment; it does not justify fixing the live installation opportunistically.

## Exact proposed scope

| Item | Proposed treatment |
|---|---|
| Original launcher, binaries and daemon | Read/record identity; no edits or replacements |
| Original profiles and disks | Preserve; copy an inactive V7 disk without hard links for the pilot |
| Added guest profile | One new `systems/unix7-web-pilot/` directory, copied ordinary V7 configuration, independent disk, one added DC11 listener |
| Selection map | Add one verified-unused, owner-approved value pointing to that profile; preserve every existing mapping/default |
| Browser endpoint | One dedicated raw loopback DC11 line 0 / V7 `tty00`, candidate port 40100; no general multiplexer listener or port hunting |
| Web bridge | New private versioned directory outside the original installation; candidate binary/configuration/tokens/certificate; manual start/stop only |
| Browser access | Loopback HTTPS/WSS through an explicitly approved SSH forward; verify the provisioned certificate; no LAN listener or global trust changes |
| Cleanup | Stop only the identified bridge; guest-safe operator shutdown; retire added selection/profile after preservation; no broad process-name kills |

The profile name and ports are proposals, not claims that those locations are currently free. Do not reuse leftover M5.3 credentials or its modified working disk. The exact selection value, current source hashes, copy paths, candidate binary hash, credential/certificate method, physical-console recovery procedure and modest workload must be recorded in the eventual authorization. No value can be safely selected from the incomplete cached public selection map. Do not preempt the owner's ongoing physical work.

## Ordered pilot checkpoints

All future host actions below take place in the **Pi Linux shell** through the separately authorized operator session. Browser actions take place on the Mac. Guest commands belong only in the verified V7 guest console; SIMH monitor commands must be visibly distinguished. These are procedure requirements, not commands executed during M5.4.

1. **Establish the physical-only baseline.** With no bridge running, record the current software/configuration identities, normal selection map and active processes. Confirm the owner's usual Screen access, physical selection and panel behavior. Agree on an inactive interval for copying V7, guest-safe recovery and power/thermal stop criteria. Verify the intended backup/restore evidence without overwriting anything. Stop if the source disk is active, machine state is uncertain, or the independent operator path is unavailable.
2. **Prepare additive, reversible files.** Preserve hashes, modes and a private copy of the selection file and source V7 configuration. Create a protected base and independent writable pilot disk, verify equal initial hashes and distinct file identities, and prepare the new profile with the one-line DC11 addition shown in the design. Confirm original profiles/disks/binaries are unchanged. Review the exact selection-map diff before applying its single approved addition. No installer edits the launcher or startup configuration.
3. **Boot through the normal path.** Set the approved selection on the physical switch register and use the original launcher **without a selection argument**. Confirm the selected profile through the independent console and current process/file evidence. There must be only the expected original simulator and panel daemon. Confirm Screen, REALCONS and physical controls through the owner's ordinary safe procedure. No browser participates in this checkpoint. A V7 boot through a new profile is not assumed successful merely because RT-11 previously booted.
4. **Verify and reserve the guest line.** Confirm that only the intended simulator owns the proposed loopback listener and that its dedicated line is free. Record PID/start time, profile/disk identity and endpoint association privately. Verify V7 and console responsiveness independently. Do not connect a probe that could consume the line, parse a banner as identity, displace a conventional terminal, or try an alternate port. Keep other conventional/serial access on separately reserved lines. The Mac lab found that immediate listener replacement can fail while an old connection is in TCP `TIME_WAIT`; a failed bind is a stop point, not a reason to change ports, modify kernel settings or keep retrying the bridge.
5. **Attach the supervised companion once.** Start the reviewed terminal-only candidate manually, with fresh private credentials and verified TLS provisioning. This is not an automatically restarted service. Authenticate the browser, explicitly connect read-only, inspect the named guest/line, and deliberately acquire keyboard ownership. Check a harmless directory listing and an unpredictable echo result against a distinct output line. A disconnect/restart invalidates the approval; a TCP connection alone does not restore it.
6. **Verify independence and ownership.** Use a second observer and a competing writer; confirm only the explicit owner can type. Close/refresh a browser and verify a fresh read-only display with no replay. Release/close the browser and confirm Screen still accepts a harmless command. Stop only the identified bridge and confirm console and physical operation continue. A guest login may hang up when its line closes; do not classify that as emulator failure or promise application survival. Do not exercise unsafe physical actions merely to test a browser failure.
7. **Exercise planned lifecycle transitions under supervision.** Stop the bridge before any intentional guest reboot, profile change, line reassignment or simulator restart. Complete the guest's own shutdown/sync procedure before moving away from its disk. Change physical selection through the normal owner procedure, with no forced launcher argument. Confirm the browser remains disconnected and the new guest runs without it. Returning to the pilot profile requires new identity checks and manual bridge startup; no lease or buffered input crosses the boundary. A retained old browser must never acquire authority on the new bridge without fresh authentication/connection/acquisition. Do not introduce a counterfeit listener on the Pi: same-port replacement is covered by isolated fixtures first.
8. **Measure modest coexistence cost.** Record bridge and simulator process RSS/CPU separately, temperature/throttling, connection count and duration. Retain ≤24 MiB idle / ≤48 MiB active / ≤64 MiB peak bridge RSS, <1% idle and <5% mean active single-core CPU targets. Measure added transport latency separately from guest response; target <100 ms p95. A short pilot cannot pass the sustained-load or emulator-throughput gates. Stop at the agreed health threshold or any effect on ordinary controls.
9. **Clean up and prove the fallback.** Release browser ownership and stop the identified bridge/forward. Through the independent operator, finish guest-safe shutdown and the appropriate normal-launcher exit; do not use the original broad stop script as a shortcut for bridge cleanup. Preserve the stopped disposable disk and evidence. Remove only the approved selection addition after confirming no intervening edits; if the map changed independently, stop for reconciliation rather than restore an old whole file. Retire the added profile and private companion files, retaining evidence as agreed. Remove temporary secrets. Verify original hashes/modes and mapping entries, absence of pilot listeners/processes, and ordinary physical-only startup with no selection argument. No reboot, autostart or power-setting change is part of rollback.

## Acceptance and stop conditions

Pass only with recorded evidence for normal physical selection, copied-media exclusivity, original Screen and panel independence, one reserved guest line, explicit keyboard ownership, no automatic attachment after loss, and a completed physical-only rollback. Compare originals before and after. Separate owner observations, executed commands and test artifacts in the report; omit credentials and private host information from publication.

Stop on unexpected guest identity, listener owner, duplicate simulator/daemon, occupied line, changed original files, uncertain writable-media use, lost Screen access, altered physical behavior, unexpected resume, or health-limit breach. Closing the bridge is a terminal disconnect, **not a CPU HALT**. The operator retains all guest and machine lifecycle decisions. Already accepted input cannot be recalled.

This supervised pilot does not prove automatic guest identification during an in-process reboot, safety against hostile local processes, physical serial expansion, durable multiuser authentication, sustained performance or production service readiness. An unexpected guest change that preserves the same connection may remain invisible to the current bridge. Require an authoritative lifecycle design before accepting unsupervised switching. Remote control and passive observation each need their own future review.

No files from this proposal were installed, no Pi commands were executed, and no permission for live execution is implied by publishing it.
