# M5.28 — Genuine isolated Ethernet with 2.11BSD

M5.28 demonstrates genuine 2.11BSD ARP, ICMP and a bidirectional TCP text exchange
through original SIMH's XU/DEUNA controller and an isolated Linux TAP. The independent
console remains usable when observation stops or the link fails. A fresh guest
and recreated TAP repeat the successful exchange after a configuration-order
fault was diagnosed. This is **guest TCP/IP**, not DECnet, a browser simulation,
Internet connectivity or physical Pi acceptance.

Starting revision: `9498805219959005df61b17cf1665848c9b8df6f`. Work took place on the
Mac in disposable ARM64 Linux. No physical Pi access, original installation change,
website edit, release, tag or upstream communication occurred. The Go/TypeScript
application and M5.27 modem remain unchanged. See the
[runbook](../../lab/m528/README.md), [observation contract](../technical/isolated-ethernet.md)
and [sanitized measurements](../../lab/m528/results/measurements.json).

## Isolation and genuine guest qualification

The exclusive namespace began with Docker network-none. Its only interfaces were
loopback and owned `tap528`; its only nonlocal route was `172.30.28.0/30`.
Linux peer `.1` and BSD `.2` used distinct locally administered MAC addresses.
There was no gateway/default route, forwarding, IPv6 route, DNS/proxy, host bridge,
physical interface or published port. Independent route queries for an external
address returned unreachable without transmitting traffic. Namespace/interface
inventories, not an attempted real-LAN probe, establish the isolation boundary.

One temporary NET_ADMIN-only root process created the TAP owned by UID 501/GID 20.
SIMH and peer ran nonroot with no capabilities and read-only roots. Optional
AF_PACKET capture needed root with **only NET_RAW** in this container setup; an
initial nonroot attempt failed with EPERM and is retained. This is isolated lab
privilege, not an approved production service. No broadly privileged container was
used. Original console operation does not depend on capture or Web Desktop.

The installed kernel is **2.11BSD UNIX #11, September 9, 2019**, with INET/NETHER/NDE
configuration and no QE driver. The retained `/netnix` has DEUNA and TCP/IP symbols;
actual boot additionally reports `attaching de0 csr 174510`. XU is DEUNA at
CSR **17774510**, interrupt vector **120**, BR5, MAC `02:00:00:52:80:02`.
No kernel modification or loadable module was required.

Only fresh disk copies were booted single-user. The `/usr` filesystem was mounted
from the working copy, and installed `ifconfig` configured `de0` UP/RUNNING with
mask `255.255.255.252`, broadcast `.3` and trailers disabled. Installed `netstat`
showed only the connected route. Existing `/etc/netstart` was not executed, because
it adds a default route. Interface symbols alone were not treated as connectivity.

| Protocol | First and final fresh-copy pings each receive 3/3 replies, zero loss |

The generated request is 23 bytes: `M528-GUEST-REQUEST-2B71\r\n`. The response is
21 bytes: `M528-PEER-REPLY-8C42\r\n`, following the separately identifiable peer
banner. Raw peer bytes and payload hashes are in the sanitized measurements.
Successful sessions close and return to the independent shell. Telnet transforms
line endings; these are printable text tests, not arbitrary binary-file transfer.
FTP, rlogin, guest network servers, DECnet and broad stack compatibility are untested.

## Failure and lifecycle results

| Case | Result and limit |
|---|---|
| Missing backend | Original binary inventory still lacks Ethernet transport; it was never replaced |
| Wrong controller / missing driver | Fresh DELQA/XQ boot attaches only loopback; both Ethernet interface queries fail; no traffic was attempted; synced/quit |
| Wrong address/subnet | `.6/30` cannot route to `.1`; bounded ping fails, console works; explicit correct reconfiguration restores route |
| Guest interface down | Ping reports no route; explicit up restores it |
| Peer absent | Connection refused; installed Telnet stays at its own prompt, requiring explicit `quit` |
| Slow peer | Bytewise 50 ms delays still produce complete distinct response; console formatting can split CR/LF |
| Partial transfer | Peer closes after nine response bytes; incomplete prefix is retained, never reported as complete |
| Duplicate/malformed frames | Separate four-frame diagnostic sends two identical valid echoes, one bad ICMP checksum and one truncated IP frame; two genuine guest replies, guest error counters and capture evidence recorded |
| Observer stopped | Actual collector TERM followed by successful guest ping and console marker; no dependency on observation |
| Link down | Owned TAP down causes SIMH write errors and missing replies; collector fails ENETDOWN without reconnect; console remains usable; explicit link-up/gate then ping succeeds |
| Peer killed | Actual active peer SIGKILL; eventual foreign closure and shell prompt preserved. The one-second closure assertion was too early and failed; no immediate-closure guarantee |
| Peer replacement | First replacement raced the old listener and failed to bind. Wait for actual exit, not merely successful signal delivery, before port reuse |
| TAP close / removal | Stopped SIMH closes its descriptor; persistent TAP loses carrier. TAP deleted/recreated only after all clients stopped; ifindex changes despite reused name/IP/MAC |
| Changed guest / simulator restart | Fresh working disk, explicit new guest ID and new capture generation; final qualified run repeats ping, TCP, console and clean exit |
| Stale observation | Offline fixture tests reject changed generation, namespace, interface index or guest ID. Real captures receive separate identities; no auto-adoption service exists |
| Explicit shutdown | Shell-prompt check and three sync replies precede simulator quit; peers/capture stop independently; owned TAP/namespace removed |

The first fresh-repeat trial exposed a significant configuration-order issue.
Manually setting DZ vector 310 disabled SIMH auto-configuration before XU was
enabled, leaving XU with **no vector**. BSD detected `de0` and sent ARP, and the
peer returned ARP replies, but the guest received no ping replies. Direct
`SET XU VECTOR=120` was rejected by this original XU implementation. Source review
of `pdp11_io_lib.c:set_vec` and `pdp11_xu.c:xu_mod` explained both observations.
The corrected sequence enables/configures XU before the manual DZ vector. An
explicit monitor gate now requires vector 120 before boot. A further harness
attempt found the inherited fixed 150 ms monitor read returned before XU's reply;
this lab now waits for the actual prompt. Both preboot failures are retained.
The final fresh-copy run passed with the corrected order and prompt barrier.

The initial normal peer timed out while operator input was delayed, and a later
string reached the shell instead of Telnet. That failed attempt was preserved;
the successful run required a fresh connection and its banner before sending.
No uncertain command was automatically replayed. The runbook documents the
Telnet prompt and process-exit checks rather than hiding these failures.

## Observations and resources

The retained summary is the networking-equipment deliverable. It has no browser
command surface and always reports current state unknown. Capture identity is
operator-attested, not inferred from IP/MAC. Existing ordinary equipment and modem
windows are unchanged. Full TCP stream reassembly, capture-drop accounting,
same-process guest replacement detection and a production observer are unqualified.

| Measurement | Actual Mac-hosted ARM64 result |
|---|---|
| SIMH short idle sample | RSS 10,396 KiB; high-water 12,640 KiB; 0.483% of one core over 2.069 s |
| Optional capture short idle sample | RSS 12,176 KiB; high-water 15,684 KiB; 0.974% of one core over 2.052 s |
| Limits | SIMH container 96 MiB; capture and peer each 32 MiB; keeper 96 MiB; build 512 MiB; all zero swap |

| Qualified fresh repeat | 22 frames, 1,920-byte PCAP, three matching echo pairs and TCP exchange; capture interval 13.017 s |
| Guest ping timing | First individual replies 33.334–66.668 ms; final three 33.334 ms. Printed average 0 is internally inconsistent and not a valid measurement |

The first capture's request-to-host-reply intervals were 2.031, 0.130 and 0.091 ms;
these TAP timestamps **exclude guest receive scheduling** and are not full RTT.
The qualified capture averaged about 1.69 frames/s over an operator-paced interval,
not a throughput benchmark. Peer session elapsed times include input delay and
are not pure network latency. SIMH statistics reset on interface reinitialization;
they must not be summed as the entire experiment's capture count. No browser
status latency or Pi performance claim is made. No companion was running in this
network lab: its future enforced 96 MiB/zero-swap requirement remains separate,
and the sum of all lab container budgets is explicitly larger.
