## Separate-kernel ARM64 investigation

QEMU 10.0.13 with the `virt` platform and software-emulated Cortex-A72 CPUs booted
Debian **6.12.118+deb13-arm64**. This is a separate kernel, unlike M5.14's containers
and VM under OrbStack 7.2.12. QEMU itself ran inside a bounded, network-none owned
container on OrbStack; the outer host is therefore still shared. The guest had
768 MiB RAM, two virtual CPUs, no network device, a native ext4 virtual block disk
and a 9p directory backed by the Mac-mounted work area. It is not a physical ARM
machine or a Pi hardware-performance surrogate.

The [QEMU platform documentation](https://www.qemu.org/docs/master/system/arm/virt.html)
describes this generic virtual board. The kernel came from Debian's authenticated
package repositories using the [ARM64 kernel package](https://packages.debian.org/trixie/arm64/linux-image-arm64).
Recorded package versions and the actual kernel hash, rather than a changing web
index, identify this run. Kernel SHA-256:
`d6d5c19445b61a820fa1718ded62d4139d0b25cb8716f6ecbbaa548023fd2053`.

| Runtime / location | Immediate copy-and-execute provisions | Result |
|---|---:|---|
| Original M5.13 / native ext4 | 8 | All exit 0 |
| Original M5.13 / shared 9p | 8 | All exit 0 |
| Current / native ext4 | 8 | All exit 0 |
| Current / shared 9p | 8 | All exit 0 |
| Each runtime under syscall tracing | 1 each | Both exit 0 |
| Copied runtime with executable permission removed | 1 refusal control | EACCES, errno 13 |

Each diagnostic child entered a cgroup with **96 MiB memory and zero swap**.
Native subprocess return codes, signal distinction, post-execution executable
hashes, file modes, mount table, limits and core-pattern metadata were saved.
Core size was bounded to 64 MiB for the owned child only; no provisioning signal
or core occurred. Syscall traces retain process/mapping/file operations with raw
write arguments to avoid logging private file contents. Actual service memory
mappings were separately preserved privately. No OOM events were recorded.
[Startup results](../../lab/m515/results/arm64-startup.json).

These results narrow the environment coverage, not the original cause. The exact
original executable can run under a different kernel and on native ext4 as well
as shared storage. They do not distinguish an intermittent runtime fault from a
Mac-mount, copy, cache, permission or scheduling interaction in the original two
untraced invocations. The old 139 records still lack native signal/core evidence.
TCG timing is not comparable to native Pi or M5.14 performance measurements.

## Resource guard and laboratory recovery

In the separate kernel, the current service refused an unbounded cgroup before
opening its HTTPS listener. With the exact 96 MiB/zero-swap limits it started
**detached**, exposed no automatically attached guest and exited normally on
SIGTERM. The final corrected run measured 10,924 KiB RSS and seven threads at one
idle instant. It recorded zero OOM events. This is a VM snapshot, not a Pi target
qualification. [Resource results](../../lab/m515/results/arm64-resource.json).

This targeted test used explicit cgroups, not a new systemd installation campaign.
The packaged unit is byte-identical to M5.14: mandatory memory guard, 96 MiB,
zero swap, `NoNewPrivileges`, private devices, strict filesystem/home protections,
`Restart=no` and disabled-by-default installation remain intact. The effective
systemd rehearsal remains [M5.14 evidence](M5.14.md).

Final cleanup caught a **separate lab teardown failure** after the first resource
check passed. The replacement `/init` text was 460 bytes, but the mounted disk
reported its old 454-byte length and ended in `powero`. Init exited 127, causing a
kernel panic. The boot also reported ext4 journal recovery. This is consistent
with journal replay undoing metadata from an offline edit made without first
settling the journal. It is not a Go crash or evidence for the original 139 exits.
The failed disk and serial trace were retained.

An attempted sparse copy on the Mac-backed share then failed with `EINVAL`
while deallocating space, leaving a short copy. The shell incorrectly continued
into later checks; that attempt was rejected. The original disk was not repaired
or overwritten. Recovery used a new ordinary byte-for-byte-verified copy on native
Linux storage, checked its filesystem, installed and compared the complete init
script, and repeated only the resource test. Remounting root read-only and calling
BusyBox poweroff explicitly completed cleanly. Both failed artifacts, the corrected
image and all logs remain private. The unsupported sparse-copy operation is a
measured filesystem limitation, **not an established explanation of exit 139**.
[Recovery record](../../lab/m515/results/lab-recovery.json).

## V7 plotting boundaries and failure classification

The disposable original SIMH/DC11 path gained a lab-only TCP tap, bounded private
byte records, unique begin/end command markers, a retained guest pipeline file,
WebSocket frame capture, offline replay through the real Tek parser and rendered
SVG counts. The original simulator and production bridge/parser were unmodified.
The conventional console remained independently owned by the lab.

After all 12 V7 terminal personality/browser cases completed, sequential plotting
passed Chromium, Firefox and WebKit. Every engine observed:

- A real begin marker and end marker from the guest console.
- **440 bytes** in the guest pipeline file, **440** at SIMH-to-bridge readback and
  **440** in browser output frames.
- **22 vectors** in offline parser replay and **22** SVG lines, with the expected
  V7 graph label and a read-only browser.

[Plot results](../../lab/m515/results/plot.json). The serial stream does not pass
through the SIMH operator PTY; that PTY carries command/marker observations while
the dedicated DC11 TCP line carries plot bytes. These boundaries are recorded
separately. The added tap and tracing may perturb timing; this run cannot rule out
an intermittent uninstrumented race.

A deliberate missing-input test then dispatched one uniquely marked command.
The guest command completed, but only **one byte** reached both serial and
WebSocket observations; parser and rendering had zero vectors. The bounded wait
failed as intended and classified `observed-stream-lacks-expected-vectors`.
No peripheral phase started. The harness did not resend the command.
[Controlled failure](../../lab/m515/results/plot-controlled-failure.json).
This tests the diagnostic boundary; it does not show that missing input caused
the historical timeout.

The original M5.14 failure can still be described only as zero observed SVG vectors
within 15 seconds after dispatch, before any device phase. Its failure log survives,
but the legacy per-engine console filename was reused by the successful attempt.
That later transcript cannot establish the earlier failed stream or guest status.
M5.15 therefore uses unique attempt directories and adds unique combined-equipment
console/failure records with phase and completion status.

A first M5.15 campaign was accidentally overlapped with another test using the same
guest. Both were stopped; that whole campaign was excluded from acceptance, the
guest was synchronized/exited and its working copy retained. A fresh copy supplied
the accepted sequential run. A new exclusive campaign wrapper refuses a second
cooperating campaign and never silently reclaims a stale/replaced lock. It does
not prevent unrelated tools from using the guest; operators must still coordinate.
Final helper review also added missing/nonfinite-count and failed-assertion
regressions so incomplete evidence cannot classify as a pass.

## Interoperability fixes and qualification

The independent client previously retained the caller's mutable preview object
across capability/status awaits. A regression changed its text and attachment
while negotiation was pending and proved that unreviewed values were published.
The client now validates and copies only the permitted primitive fields before
its first await. Malformed identifiers, invalid Unicode, unexpected fields and
invalid viewer revisions are refused before network access.

A second regression made the optional module's provider resolve successfully
after browser cancellation. The old path attempted to publish that late answer.
The module now checks cancellation before requests, after headers and after the
body. The independent selection client also rechecks cancellation after bounded
body reads. These are consumer-side delivery protections; neither can recall
submitted data or guarantee that a provider stopped work.

Nine independent-client cases, six optional-app route cases, the Go race suite
and an opt-in **actual TLS** Go-server/Node-client test passed. The latter covers
credential/Origin separation, unknown OS/CPU status, exact receipts, stale epochs,
one-winner concurrent HTTP publication, controlled expiry/lifetime loss, adapter
restart, malformed/oversized requests and denied control routes. Its fixture
control endpoints exist only in `_test.go`; expiry and browser lifetime changes
are injected, not new independent observer acceptance.

Gateway cancellation, busy/no-queue behavior, provider errors, quotation safeguards,
offline references and exact arithmetic remain covered by the existing passing
Go/TypeScript suites. There was no new full upstream application or real-model
sharing campaign; genuine app/model evidence remains M5.12. No upstream code or
Rolf communication was involved. [Qualification](../../lab/m515/results/contract.json)
and [external-review packet](../technical/M5.15-interoperability-review.md).
The packet is prepared by the implementer and is not an independent audit.
