## Startup and resource safeguards

The extracted ARM64 service ran in a disposable, network-none Linux container with
read-only root, no added capabilities, 64-process ceiling, 96 MiB kernel memory
limit and zero swap. The service's guard accepted the actual cgroup settings;
HTTPS returned 200, local status showed the only configured line detached with
zero viewers, and a listening loopback sentinel recorded **zero guest dial attempts**.
The process exited cleanly. A single idle observation measured 10,596 KiB resident
memory and 16,404,480 bytes for the whole container including the Python observer;
no cgroup OOM events occurred. This is a short smoke check, not a sustained load,
CPU/latency benchmark or a Raspberry Pi measurement.

Separate runs refused startup with a 128 MiB limit and with nonzero permitted swap,
before reading configuration or opening service listeners. Missing/unreadable
controller and malformed-value cases remain covered by the Go suite. The shipped
unit still requires the memory guard, `MemoryMax=96M`, `MemorySwapMax=0` and
`Restart=no`; nothing was installed or enabled. The actual Pi's disabled memory
controller remains a deployment blocker.

The first private startup harness used a non-private control directory. The
application correctly rejected it. The harness was corrected to mode 0700, then
passed; the original failure log is preserved. No application fix was necessary.
All disposable startup containers were removed. No guest or simulator was started.
