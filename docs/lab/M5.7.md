# M5.7: all-DOWN switch discrepancy reproduced

**November 19, 2026 (America/Phoenix). Test A failed its expected-value checkpoint.** With the owner confirming every SR0–SR21 paddle DOWN and exclusive maintenance, all 20 original-scanner samples reported decimal `1`: SR0 asserted, every other SR bit clear. The unchanged selection map resolves that value to `0001` → `rsx11mp`. This reproduces the selection discrepancy without starting a guest or executing the launcher. It does not establish the physical cause or prove that the earlier M5.5 event had exactly the same cause.

The pattern sequence stopped after Test A. Tests B, C and D were neither requested nor run. There was no retry to obtain passing evidence, no original-source correction, no forced selection and no accepted physical-selection checkpoint. The Pi was left powered on and stopped after verified cleanup.

## What the evidence narrows down

The reviewed upstream source is pinned at [`26d20beda0c6b5a1d3a5cb3d7a4dd494e02bff75`](https://github.com/obsolescence/pidp11/tree/26d20beda0c6b5a1d3a5cb3d7a4dd494e02bff75). Local analysis used that retained checkout and the verified installed source; no upstream implementation was patched.

| Question | Finding and limit |
|---|---|
| SR0 signal path | In `src/11_pidp_server/scanswitch/scansw.c`, row 0 is GPIO16 and column 0 is GPIO26. A zero returned by `gpio_get_level(26)` while row 0 is selected sets raw bit 0. Raw `1` is consistent with this one asserted position. This is source interpretation, not an independent voltage measurement. |
| Polarity | The scanner treats a low column reading as an asserted bit. The BCM2835 implementation reads the level register without inversion. One asserted bit with the others clear does not look like a simple inversion of all SR bits, but physical contact orientation and wiring remain unverified. |
| Exit status | The original C program prints both rows combined and returns its first row; the OS exposes the low eight return bits. Status `1` agrees with stdout `1` and is not by itself an execution failure. |
| Selection conversion | The unchanged launcher uses raw value modulo 262144, then octal formatting and `getsel.sh`. Zero stays zero. Isolated Linux checks using the original resolver and captured map gave 0→0000→IDLED, 1→0001→RSX and 15→0017→default IDLED. No launcher or scanner executed in that check. |
| Timing | Each row requests a 10 µs pause before reading its columns. Actual settling time and electrical levels were not measured. The recorded wrapper durations cannot establish whether that pause is sufficient. |
| Process races | No conflicting process/device owner was found before, during diagnostic guards or after sampling. A running launcher/panel-daemon race is not required to reproduce this observation. Transient interference between checks and the historical M5.5 sequence are not conclusively excluded. |
| Stability | All 20 readings agreed over approximately 5.91 seconds. That establishes stability for this capture, not a permanent fault or the absence of intermittent behavior. |

Possible causes remain along the SR0 contact, assembly/wiring and GPIO scanning path, including electrical settling or initialization behavior. The evidence does not yet distinguish them. No software change, live electrical probing, disassembly or forced numeric boot is justified as an automatic remedy.

The owner was informed of the original scanner's operations before confirming Test A. LED rows 20–25 become inputs; columns 26, 27, 4–13 and switch rows 16–18 become inputs with pull-ups. Rows 16 and 17 are driven low in turn, sampled after the requested pause, then returned to input. This is GPIO initialization and sampling, not passive file inspection. After the bounded diagnostic exited, a fresh administrative inventory found no Screen session, emulator/panel/bridge process or open/mapped GPIO owner. The diagnostic lock, confirmed absent before this run, was removed after validating its metadata and obtaining its exclusive lock. The cleanup helper itself was then hash-checked and removed. Captured samples, map and private inventories were retained. Cleanup performed no GPIO operation.

The Pi remains powered on in its normal stopped operating state, with no guest or companion service started. GPIO direction/pull state was left as the original scanner establishes it; there was no invented restoration command or claim of an electrical reset.
