# M4.2 findings, validation and remaining risks

M4.2 delivers a cohesive local desktop and a separately isolated passive-observation laboratory. All work occurred on the Mac or its network-none Linux ARM64 environment. The production Pi, GPIO, official installation and guest images were not accessed. Production integration still requires separate authorization.

## Delivered desktop and parity findings

The [IMSAI inventory](../research/imsai-inventory.md) examines the public v1.14.0 distribution containing GUI 1.15.0, not just screenshots. It identifies a purpose-built window manager, xterm/CodeMirror and device-specific HTTP/WebSocket paths. TTY2/TTY3 assets are present but removed by the inspected startup; TAPE is paper tape, the printer is a separate browser window, and graphical hard-disk mounting is incomplete. Frontend analysis does not establish server-side authentication or hardware behavior. No packaged IMSAI code or artwork is redistributed.

The delivered [parity matrix](../research/imsai-parity.md#delivered-m42-status) distinguishes working prototypes from later integration. PiDP now has move/resize/minimize/restore/maximize/fullscreen-request/close/reopen, focus/stacking, a taskbar, geometry preferences, keyboard shortcuts and touch controls. Four mock terminals have independent keyboard ownership. Disk and tape workflows check compatibility and stopped state; paper tape and printer operate on bounded local bytes/jobs and downloadable output. OS profiles have explicit simulated start/stop; host diagnostics remain unavailable rather than invented.

The [frontend architecture](../frontend-m42.md) documents modules, limits, terminal compatibility and CSP. Two supplied DIGITAL originals remain byte-identical, with provenance and proportion-preserving derivatives. The [panel calibration](../research/panel-m42-calibration.md) corrects photographic proportions, positions, octal colors and red lamps. Full and desktop views share one model. Mechanical dimensions, typography, paddles and knobs retain documented approximations; native physical behavior is not claimed.

## Observation and recovery findings

The [observation/security design](M4.2-observation.md) copies an existing REALCONS cycle into a bounded nonblocking Unix datagram channel. The Go observer has **no RPC client, broker, control, terminal-input or media route**. Multiple viewers do not add physical GETs or change program-99 registration. Receiver absence/full queues drop copies and do not block the original control route. Unavailable, fresh, stale and disconnected states are distinguished.

Six independent capabilities are represented and tested. Only read-only observation is exposed by the new lab service. Token login, expiring HttpOnly/SameSite cookies, exact Origin/Host checks, logout CSRF, stream limits, expiry and write rejection are implemented. TLS/Secure-cookie provisioning, production identities/audit and terminal/media services remain unimplemented; loopback auth is not a LAN deployment recipe.

The separate bounded-UDP-call experiment confirmed consumer quiescence approximately **309 ms** after a held response and broker kill in the recorded run. It does not establish an end-to-end stop deadline or bound rpcbind discovery. Restart did not automatically rearm/resume. Original M4's stale START-release counterexample remains reproduced; M4.1's consumer fencing still rejects its tested delayed and queued commands. Committed actions cannot be reversed, and a disarmed lease is not synonymous with confirmed quiescence.

## Performance and optimization findings

See [machine-readable measurements](m42/measurements.json) and the raw observation, browser and instruction reports. CPU percentages use **100% = one core**. These are Mac/OrbStack measurements, not Pi results. Browser scripting/render-task CPU is a Chromium metric and is not total browser OS CPU; JS heap is not tab RSS. Several development workloads ran concurrently, so these figures are characterization rather than a controlled Pi acceptance benchmark.


| Measured workload | Result | Interpretation |
|---|---|---|
| Eight observers, 300 seconds | Observation service 2.00% one-core CPU; peak RSS 11.58 MiB; final RSS 7.88 MiB | Additional observation service only, Mac-hosted Linux |
| Physical input polling | 44.09 GET/s baseline; 44.74 GET/s with eight observers | No observer-dependent increase; registrations unchanged |
| Capture-to-observer latency | Maximum 60 ms over 35,845 fresh frame deliveries | Local loopback, no LAN/physical latency claim |
| Four mock terminals, 300 commands over 300 seconds | Retained JS heap 4.46 MiB after collection; sampled peak 5.58 MiB | Includes bounded history/scrollback filling; not total browser RSS or leak proof |
| Browser rendering workload | 2.90% renderer-task CPU; 89.9 ms p95 interaction through two animation frames | Includes automation/focus/input overhead; not guest command completion |
| Browser assets | Core 26.4 KiB gzip; terminal JS/CSS/addon/wrapper 82.5 KiB gzip | Self-contained complete file 429,255 bytes |
| Static ARM64 mock executable | 6,488,226 bytes | Stripped, statically linked, all assets embedded; never deployed to Pi |

The ordinary compiled service embeds the application, while rendering and terminal work remain in the user's browser. The normal browser bundle splits terminal code; the self-contained checkpoint deliberately includes it all. The two terminal packages add approximately 83 KiB gzip including their wrapper/addon, while the core remains far below the 150 KiB gzip target. No new Go runtime dependency was added.

The rerun M4.1 idle broker sample still measured **2.40% of one host core**, above the <1% target. Required physical mediation, 20 ms maintenance ticks, map/JSON copies and RPC codec allocations remain real costs. The existing reusable read buffer measures about 12.3 KiB/151 allocations per physical read versus 77.9 KiB/152 for the prior allocation path. Observation snapshot+JSON costs about 4.2 KiB/71 allocations in the Mac microbenchmark. These indicate candidate profiling work; they do not justify slowing safety polling or removing synchronization.

The original M4.1 short disabled-patch result (~4.84%) is retained. The M4.2 short rerun varied to -1.03%; the longer **seven alternating billion-instruction samples** measured +0.23% median wall time (+0.17% process CPU) for fenced-disabled versus original. Observation-disabled measured -1.70% wall time. Negative changes are not evidence of a guaranteed speedup. Build layout, sampling and host variability matter; real guest workloads, patch-enabled overhead and Pi thermals remain unmeasured. No instruction-loop hook was added for passive observation.

Retain the Pi 3B+ targets: ≤24 MiB idle backend RSS; ≤48 MiB active/≤64 MiB peak; <1% idle and <5% mean active CPU; <3% emulator throughput impact; <100 ms p95 panel freshness/acknowledgment; bounded queues and no unbounded memory trend. Five-minute results do not meet the planned 30-minute target-hardware acceptance duration. See [roadmap/resource budget](../roadmap.md).

## Remaining risks and next milestone

| Risk / unknown | Current evidence | Required next step |
|---|---|---|
| Physical POWER/LOCK and boot-selection semantics | Not exercised; interlock's disarmed forcing remains lab-only | Preserve original Mode A; separately authorized physical behavior audit |
| Unbounded discovery/other consumer I/O | Per-call UDP timeout experiment succeeds; no total deadline | Bound discovery and call sequences, distinguish disarmed/quiescent, supervisor/operator recovery protocol |
| In-flight/committed execution | Consumer tickets reject tested stale commands; committed DEP persists | Preserve failure tests; never equate fencing with rollback |
| Native Safari and hardware touch/accessibility | Automated three-engine tests pass; native app was inaccessible | Native Safari, real tablet and assistive-technology sessions |
| Terminal compatibility and real sessions | Mature renderer, four mock sessions, two original DZ transport fixtures | DEC conformance/encoding/keypad tests, bounded byte streams and guest configuration; no SSH/Screen takeover |
| Media and guest lifecycle | Functional RAM-only guards | Backend authoritative image exclusivity, validated attach/eject and guest-safe shutdown after authorization |
| Auth beyond loopback | Capability boundaries and lab auth implemented | TLS/WSS, Secure cookies, service identities, provisioning/revocation/logout/audit UX |
| Publisher provenance | Owner-only local socket, complete schema validation | Private runtime path and process/UID isolation; root/same-UID attacker out of scope |
| Resource acceptance | Five-minute host samples and longer instruction trial | 30-minute repetitions, workload/thermal control, later authorized Pi RSS/PSS/CPU measurements |

Recommended **M4.3: offline integration hardening**. Complete terminal conformance fixtures, LAN authentication/session design, publisher identity isolation and a bounded recovery budget; extend sustained resource tests. Report readiness before proposing an explicitly authorized read-only Pi audit/pilot. Neither backup completion nor this checkpoint authorizes production access or remote control.
