The independently runnable client is optional. It uses fixed HTTPS destinations,
separate application/model credentials, immutable approved text, publication epochs
and exact receipts. Expiry, revocation and cancellation retire authority; unknown
OS identity stays unknown. Neither application gains original-console or simulator
control. The current optional app experiment uses a pinned local modification;
this is not upstream support. A future agreed provider interface could avoid a
permanent fork, but that outcome depends on upstream decisions.

## Proposed future route — design only

A negotiated opt-in version could advertise a `selected-text-receipt-required`
capability and a new `/selected-text` route. That route would reject absent,
expired or substituted receipts. Existing 0.1 `/screen` callers would retain their
current behavior until deliberately migrated. A new client must refuse an unknown
version or missing capability rather than silently downgrade. Both paths must
share the same epoch, immutable snapshot and revocation state; creating two
independent consent stores would introduce ambiguity.

No route or version is added in M5.17. Before implementation, agree on version
negotiation, page scope versus shared slot, credential custody and the limited
meaning of history clearing. Revocation cannot recall text already delivered to
another page or model. Tests should cover old/new clients together, missing and
stale receipts, global revoke, identical-text replacement, expiry, cancellation,
restart and unknown guest identity. Avoid finalizing names or compatibility policy
without feedback.
