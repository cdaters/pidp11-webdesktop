## Five decisions, with compatibility consequences

| Decision | Existing experiment / 0.1 | Rolf's agreed direction | Proposed change and lifecycle consequence | Compatibility / planned test |
|---|---|---|---|---|
| 1. Optional read-only provider | Pinned modified app, opt-in `PIDP11_READONLY`; original tools intercepted in that experimental mode | Native optional provider, disabled by default; independent authentication and normal modes | Consumer-only provider entry point; enabling it cannot enable tools or console access; no integration prerequisite | No claim of native upstream support. Test disabled startup/no calls, independent login and mode changes (C01, C16) |
| 2. Selected-text naming and receipts | `/api/pidp11/screen` permits absent header. Independent client sends header; modified app checks returned receipt after read | Dedicated `/selected-text`, exact receipt mandatory every time; distinct from full GNU Screen `read_screen` | Propose full `/api/pidp11/v0.2/selected-text`; reject absent/malformed/mismatched receipts before text; no fallback | Preserve 0.1 unchanged; exclusive future 0.2 profile prevents legacy bypass. Test missing/duplicate/wrong receipts, no fallback and legacy regression (C04, C16, C20) |
| 3. Web Desktop owns consent/publication | Modified companion UI previews/publishes; its backend holds both adapter tokens. Desktop's own sharing goes to its internal Companion, not this adapter | Desktop owns selection, preview, approval and publisher credential; Hacker Replicant only consumes | Add future same-origin Desktop consent backend with immutable preview and trusted source-view binding. Manually transfer a receipt, never a bearer token; consumer separately authenticates and asks to include | Existing helper/client are not drop-in 0.2 consumers. Test exact preview, no browser token, no network on launch/paste and separate credentials (C02, C03, C13, C14) |
| 4. One shared slot | One adapter selection, publication epoch and random receipt; any writer can replace/revoke | Keep one shared slot; replacement retires old receipt | Retain global replacement/revoke, no page/multiuser scope. Explain that one page can retire another's excerpt | Same conceptual model, new version/profile only. Test competing publishers, identical-text replacement and delayed publish after revoke (C07, C08) |
| 5. Expiry/revoke and local history | Modified UI clears receipt/include flag, emits `pidp11-revoke`; prepared app resets future history and cancels request | Clear local receipt and signal local history reset; no global erasure promise | Proposed local reset event in each application, expiry-bound state, no restored receipt after reconnect; remote revoke noticed on read or expiry, not immediate broadcast | Old event untouched. Already delivered text/model inputs remain outside recall. Test local clearing, delayed responses, retained-history exclusion and truthful notices (C09, C15, C17, C18) |

Agreed directions do not by themselves approve `0.2-proposed`, its `/v0.2` prefix,
manual envelope, role-based status access, new success body or exclusive migration
profile. Those are concrete recommendations for owner/Rolf review.

## Implementation sequence and review questions

1. Owner/Rolf review the proposal and handoff. Record exact version/path/envelope
   choices; agreement on architecture is not approval to implement.
2. Separately authorize a new adapter profile and role-separated clients, then
   exercise the new conformance cases beside unchanged legacy tests.
3. Implement Desktop consent/identity binding/receipt copy without model actions;
   qualify delayed cancellation and source retirement before any actual guest text.
4. If Rolf chooses, implement an independently authenticated native consumer under
   his own conventions. Our team can provide fixtures; upstream work/maintenance is
   not presumed, nor is another permanent patch to his app.
5. Qualify actual optional-app interaction with synthetic text first, then separately
   authorized genuine excerpts. Record exact revisions, failures and retained limits
   before claiming compatibility or retiring the legacy experiment.

Only three review questions remain: Are the proposed versioned route/schema and
exclusive migration profile suitable? Is manual receipt import a useful initial
consumer workflow within 30 seconds? Where would the optional consumer and local
history reset fit Hacker Replicant's own UI/session lifecycle? None reopens the
five agreed architectural directions or asks Rolf to maintain our adapter.
